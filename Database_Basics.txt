# 1. DBMS FUNDAMENTALS & ARCHITECTURE

## 1.1 Database

A **database** is an organized collection of logically related data that can be stored, accessed, managed, and updated efficiently.

### Example

A university database may contain:

* Student information
* Department information
* Course information
* Faculty information
* Enrollment records
* Examination records

---

## 1.2 Database Management System (DBMS)

A **Database Management System (DBMS)** is software that provides an interface for creating, storing, retrieving, updating, securing, and managing data in a database.

### Major Functions of a DBMS

1. Data storage and organization
2. Data retrieval
3. Data insertion, modification, and deletion
4. Security and authorization
5. Integrity constraint enforcement
6. Transaction management
7. Concurrency control
8. Backup and recovery
9. Query processing and optimization
10. Data independence

---

## 1.3 Advantages of DBMS

* Reduces unnecessary data redundancy
* Improves data consistency
* Supports controlled data sharing
* Provides security and authorization
* Enforces integrity constraints
* Supports concurrent access
* Provides transaction management
* Provides backup and recovery
* Provides data independence
* Simplifies data management

---

## 1.4 Three-Level Database Architecture

The three-level architecture separates the user view, logical structure, and physical storage of a database.

### 1. External Level

The **external level** describes how individual users or applications view the database.

Different users may have different views of the same database.

### 2. Conceptual Level

The **conceptual level** describes the complete logical structure of the database.

It includes:

* Entities
* Relationships
* Attributes
* Constraints
* Tables and their logical relationships

### 3. Internal Level

The **internal level** describes how data is physically stored.

It deals with:

* Files
* Pages
* Blocks
* Record layouts
* Indexes
* Storage structures

### Architecture

```text
Users / Applications
        ↓
External / View Level
        ↓
Conceptual / Logical Level
        ↓
Internal / Physical Level
        ↓
Physical Storage
```

---

## 1.5 Data Independence

Data independence means changing one level of the database architecture without requiring unnecessary changes at higher levels.

### Physical Data Independence

The ability to change the **internal/physical schema** without changing the conceptual schema.

Examples:

* Changing file organization
* Adding an index
* Changing storage structures
* Changing page allocation

### Logical Data Independence

The ability to change the **conceptual schema** without requiring changes to external views or application programs.

Examples:

* Adding a new attribute
* Adding a new relation
* Modifying logical relationships

### Key Distinction

| Type                       | Change occurs at | Higher level protected |
| -------------------------- | ---------------- | ---------------------- |
| Physical Data Independence | Internal level   | Conceptual level       |
| Logical Data Independence  | Conceptual level | External level         |

---

## 1.6 Schema and Instance

### Schema

The **schema** is the structure or design of a database.

Example:

```text
Student(RollNo, Name, Marks, DeptID)
```

The schema normally changes infrequently.

### Instance

An **instance** is the actual data stored in the database at a particular point in time.

Example:

```text
101 | Rahul | 85 | 10
102 | Priya | 91 | 20
```

The instance changes frequently.

---

## 1.7 Database Administrator (DBA)

A DBA is responsible for managing and maintaining the database system.

### Major Responsibilities

* User authorization
* Security management
* Backup and recovery
* Storage management
* Performance monitoring
* Database maintenance
* Integrity enforcement
* Access control
* Resource management

---

# 2. RELATIONAL MODEL, KEYS & INTEGRITY CONSTRAINTS

## 2.1 Relational Model

The relational model represents data using **relations**, commonly implemented as tables.

### Basic Terminology

| Relational Term | Common Database Term  |
| --------------- | --------------------- |
| Relation        | Table                 |
| Tuple           | Row                   |
| Attribute       | Column                |
| Domain          | Allowed set of values |
| Cardinality     | Number of tuples      |
| Degree          | Number of attributes  |

---

## 2.2 Keys

A key is an attribute or combination of attributes used to identify tuples.

### Super Key

A **super key** is any set of attributes that uniquely identifies a tuple.

A super key may contain unnecessary attributes.

### Candidate Key

A **candidate key** is a minimal super key.

It uniquely identifies a tuple and contains no unnecessary attribute.

### Primary Key

A **primary key** is the candidate key selected as the main identifier of tuples.

Properties:

* Uniquely identifies tuples
* Cannot contain NULL values
* A table has one primary-key constraint
* It may consist of multiple attributes

### Alternate Key

A candidate key that was not selected as the primary key.

### Foreign Key

A foreign key is an attribute or set of attributes that references a candidate/primary key of another relation.

### Composite Key

A key consisting of more than one attribute.

Example:

```text
Enrollment(StudentID, CourseID, Grade)
```

`(StudentID, CourseID)` may form a composite key.

---

## 2.3 SQL Example: Keys

```sql
CREATE TABLE Department (
    DeptID INT PRIMARY KEY,
    DeptName VARCHAR(50)
);

CREATE TABLE Student (
    RollNo INT PRIMARY KEY,
    Name VARCHAR(50),
    Marks INT,
    DeptID INT,
    FOREIGN KEY (DeptID)
        REFERENCES Department(DeptID)
);
```

---

## 2.4 Integrity Constraints

### Domain Integrity

Ensures that attribute values belong to their valid domain.

Examples:

* Integer values for integer columns
* Valid date values
* Restricted values using CHECK

### Entity Integrity

A primary key cannot contain NULL values.

### Referential Integrity

A foreign-key value must correspond to an appropriate referenced key value, subject to NULL and referential-action rules.

### Key Constraint

Ensures that key values uniquely identify tuples.

---

## 2.5 NULL

NULL represents an unknown, missing, or not-applicable value.

NULL is not:

* Zero
* An empty string
* False

### Correct NULL Comparison

```sql
SELECT *
FROM Student
WHERE Marks IS NULL;
```

```sql
SELECT *
FROM Student
WHERE Marks IS NOT NULL;
```

Using:

```sql
Marks = NULL
```

does not correctly test for NULL.

# 3. FUNCTIONAL DEPENDENCIES & ATTRIBUTE CLOSURE

## 3.1 Functional Dependency

A functional dependency is written as:

```text
X → Y
```

It means that if two tuples have the same value of `X`, they must have the same value of `Y`.

`X` is called the **determinant** and `Y` is the **dependent**.

---

## 3.2 Types of Functional Dependencies

### Trivial Functional Dependency

```text
X → Y
```

is trivial when:

```text
Y ⊆ X
```

Example:

```text
AB → A
```

### Non-Trivial Functional Dependency

```text
X → Y
```

where:

```text
Y ⊄ X
```

### Completely Non-Trivial Functional Dependency

When:

```text
X ∩ Y = ∅
```

---

## 3.3 Armstrong's Axioms

### Reflexivity

If:

```text
Y ⊆ X
```

then:

```text
X → Y
```

### Augmentation

If:

```text
X → Y
```

then:

```text
XZ → YZ
```

### Transitivity

If:

```text
X → Y
Y → Z
```

then:

```text
X → Z
```

---

## 3.4 Derived Rules

### Union

If:

```text
X → Y
X → Z
```

then:

```text
X → YZ
```

### Decomposition

If:

```text
X → YZ
```

then:

```text
X → Y
X → Z
```

### Pseudotransitivity

If:

```text
X → Y
WY → Z
```

then:

```text
WX → Z
```

---

## 3.5 Attribute Closure

The closure of attribute set `X`, written as:

```text
X+
```

is the set of all attributes functionally determined by `X`.

### Example

Consider:

```text
R(A, B, C, D, E)
```

with:

```text
A → B
B → C
CD → E
```

Find:

```text
AD+
```

Start:

```text
AD+ = {A, D}
```

Using:

```text
A → B
```

we get:

```text
{A, B, D}
```

Using:

```text
B → C
```

we get:

```text
{A, B, C, D}
```

Now:

```text
CD → E
```

therefore:

```text
AD+ = {A, B, C, D, E}
```

Since the closure contains all attributes, `AD` is a super key.

If neither `A` nor `D` can be removed while preserving the full closure, `AD` is a candidate key.

---

## 3.6 Candidate Key Identification

A practical procedure:

1. Identify attributes that do not appear on the RHS of any FD.
2. Such attributes generally need to be present in every candidate key.
3. Compute the closure of a candidate attribute set.
4. If closure contains all relation attributes, it is a super key.
5. Test minimality.
6. A minimal super key is a candidate key.

### Important Principles

* `A → B` does not imply `B → A`.
* A determinant is not automatically a candidate key.
* Closure containing all attributes means super key.
* Candidate key additionally requires minimality.

## 4.3 DELETE vs TRUNCATE vs DROP

| Operation |      Removes Rows | Removes Structure | WHERE |
| --------- | ----------------: | ----------------: | ----: |
| DELETE    | Selected/all rows |                No |   Yes |
| TRUNCATE  |          All rows |                No |    No |
| DROP      |    Data and table |               Yes |    No |

---

## 4.4 Aggregate Functions

Common aggregate functions:

```text
COUNT()
SUM()
AVG()
MIN()
MAX()
```

### COUNT Differences

```sql
COUNT(*)
```

Counts rows.

```sql
COUNT(Marks)
```

Counts non-NULL values in `Marks`.

```sql
COUNT(DISTINCT DeptID)
```

Counts distinct non-NULL department values.

---

## 4.5 GROUP BY and HAVING

`GROUP BY` forms groups of rows.

`HAVING` filters groups after grouping.

```sql
SELECT DeptID, AVG(Marks) AS AverageMarks
FROM Student
GROUP BY DeptID
HAVING AVG(Marks) > 75;
```

### WHERE vs HAVING

| WHERE                             | HAVING                                  |
| --------------------------------- | --------------------------------------- |
| Filters rows                      | Filters groups                          |
| Applied before grouping           | Applied after grouping                  |
| Normally used with row conditions | Commonly used with aggregate conditions |

---

## 4.6 Logical Processing Order

A simplified logical order is:

```text
FROM
↓
WHERE
↓
GROUP BY
↓
HAVING
↓
SELECT
↓
DISTINCT
↓
ORDER BY
```

---

## 4.7 Joins

### INNER JOIN

Returns matching rows from both relations.

```sql
SELECT S.Name, D.DeptName
FROM Student S
INNER JOIN Department D
ON S.DeptID = D.DeptID;
```

### LEFT JOIN

Returns all rows from the left relation and matching rows from the right relation.

### RIGHT JOIN

Returns all rows from the right relation and matching rows from the left relation.

### FULL OUTER JOIN

Returns rows from both relations, matching where possible.

### SELF JOIN

A table is joined with itself.

```sql
SELECT E.Name, M.Name AS Manager
FROM Employee E
JOIN Employee M
ON E.ManagerID = M.EmployeeID;
```

---

## 4.8 Join Multiplication

In a one-to-many relationship, joining tables can produce multiple result rows for a single row from the first table.

When counting entities after such joins, `COUNT(DISTINCT ...)` may be necessary.

```sql
SELECT COUNT(DISTINCT S.RollNo)
FROM Student S
JOIN Enrollment E
ON S.RollNo = E.StudentID;
```

---

## 4.9 Subqueries

A subquery is a query nested inside another SQL statement.

### IN

Tests membership in a result set.

```sql
SELECT Name
FROM Student
WHERE DeptID IN (
    SELECT DeptID
    FROM Department
    WHERE DeptName = 'CSE'
);
```

### EXISTS

Returns true when the subquery produces at least one qualifying row.

```sql
SELECT S.Name
FROM Student S
WHERE EXISTS (
    SELECT 1
    FROM Enrollment E
    WHERE E.StudentID = S.RollNo
);
```

### ANY

The comparison must be true for at least one value returned by the subquery.

### ALL

The comparison must be true for every value returned by the subquery.

---

## 4.10 Correlated Subquery

A correlated subquery refers to a column from the outer query.

```sql
SELECT S.Name, S.Marks
FROM Student S
WHERE S.Marks >
(
    SELECT AVG(S2.Marks)
    FROM Student S2
    WHERE S2.DeptID = S.DeptID
);
```

The inner query is evaluated with respect to the current outer-row context.

---

## 4.11 NULL and Three-Valued Logic

SQL conditions can evaluate to:

```text
TRUE
FALSE
UNKNOWN
```

UNKNOWN commonly occurs when NULL participates in a comparison.

Important logical behavior:

```text
FALSE AND UNKNOWN = FALSE
TRUE OR UNKNOWN = TRUE
```

Use:

```sql
IS NULL
IS NOT NULL
```

instead of equality comparisons with NULL.

When designing anti-match queries, `NOT EXISTS` can avoid the NULL-related behavior that can occur with `NOT IN`.

---

## 4.12 Set Operations

### UNION

Combines results and removes duplicate rows.

### UNION ALL

Combines results and retains duplicates.

### INTERSECT

Returns rows common to both result sets.

### EXCEPT

Returns rows present in the first result but not the second.

The participating result sets must have compatible structures.

---

## 4.13 CASE Expression

```sql
SELECT Name,
       CASE
           WHEN Marks >= 90 THEN 'A'
           WHEN Marks >= 80 THEN 'B'
           ELSE 'C'
       END AS Grade
FROM Student;
```

Conditions are evaluated in the order written.

---

## 4.14 DISTINCT

`DISTINCT` removes duplicate result rows based on the **combination of all selected expressions**.

Example:

```sql
SELECT DISTINCT DeptID, Marks
FROM Student;
```

The pair `(DeptID, Marks)` is considered as a combination.

# 5. NORMALIZATION

## 5.1 Purpose of Normalization

Normalization organizes relations to reduce:

* Data redundancy
* Update anomalies
* Insertion anomalies
* Deletion anomalies

---

## 5.2 First Normal Form — 1NF

A relation is in 1NF when attribute values are atomic and repeating groups are eliminated.

Example of non-atomic design:

```text
StudentID | PhoneNumbers
101       | 9876, 8765
```

A normalized design stores phone values separately.

---

## 5.3 Second Normal Form — 2NF

A relation is in 2NF when:

1. It is in 1NF.
2. No non-prime attribute is partially dependent on a candidate key.

### Partial Dependency

A non-prime attribute depends on only part of a composite candidate key.

A partial dependency requires a composite candidate key.

If every candidate key is single-attribute and the relation is in 1NF, the relation is automatically in 2NF.

---

## 5.4 Prime and Non-Prime Attributes

### Prime Attribute

An attribute belonging to at least one candidate key.

### Non-Prime Attribute

An attribute that belongs to no candidate key.

---

## 5.5 Third Normal Form — 3NF

For every non-trivial functional dependency:

```text
X → A
```

at least one must hold:

1. `X` is a super key, or
2. `A` is a prime attribute.

3NF allows certain dependencies involving prime attributes that BCNF does not allow.

---

## 5.6 Boyce-Codd Normal Form — BCNF

A relation is in BCNF if for every non-trivial functional dependency:

```text
X → Y
```

`X` must be a super key.

### Relationship

```text
BCNF is stricter than 3NF.
```

Therefore:

```text
BCNF ⇒ 3NF
```

but a relation can be in 3NF without being in BCNF.

---

## 5.7 Example: 3NF but not BCNF

Consider:

```text
R(Student, Course, Instructor)
```

with:

```text
Course → Instructor
Instructor → Course
```

Possible candidate keys:

```text
(Student, Course)
(Student, Instructor)
```

Both `Course` and `Instructor` are prime attributes.

The relation can satisfy 3NF because the RHS attributes are prime.

However, `Course` and `Instructor` are not necessarily super keys, so BCNF can fail.

---

## 5.8 Lossless Decomposition

A decomposition is **lossless** if joining the decomposed relations recreates the original relation without generating spurious tuples or losing information.

For a binary decomposition of `R` into `R1` and `R2`, a standard condition is that:

```text
(R1 ∩ R2) → R1
```

or

```text
(R1 ∩ R2) → R2
```

must hold under the relevant functional-dependency closure.

---

## 5.9 Dependency Preservation

A decomposition is dependency preserving if the original functional dependencies can be enforced using the decomposed relations without requiring joins of those relations.

### Important Distinction

```text
Lossless decomposition
```

and

```text
Dependency preservation
```

are separate properties.

---

# 6. TRANSACTIONS & SERIALIZABILITY

## 6.1 Transaction

A **transaction** is a logical unit of database operations that should be treated as a single unit of work.

### Example: Bank Transfer

```text
T1:

Read(A)
A = A - 500
Write(A)

Read(B)
B = B + 500
Write(B)

COMMIT
```

The transfer should not leave the database with only one account updated.

---

## 6.2 ACID Properties

### Atomicity

All operations of a transaction occur, or the transaction is rolled back.

### Consistency

A transaction takes the database from one valid state to another valid state while preserving defined constraints.

### Isolation

Concurrent transactions are controlled so that intermediate effects do not cause unacceptable interference.

### Durability

Once a transaction is committed, its effects survive appropriate system failures according to the recovery protocol.

---

## 6.3 Transaction States

```text
             Partially Committed
            /                   \
Active -----------------------> Committed
  |
  ↓
Failed
  |
  ↓
Aborted
  |
  ├── Restart
  └── Terminate
```

---

## 6.4 COMMIT

`COMMIT` successfully completes the current transaction.

```sql
START TRANSACTION;

UPDATE Account
SET Balance = Balance - 500
WHERE AccountID = 101;

UPDATE Account
SET Balance = Balance + 500
WHERE AccountID = 102;

COMMIT;
```

---

## 6.5 ROLLBACK

`ROLLBACK` undoes changes made by the current uncommitted transaction.

```sql
START TRANSACTION;

UPDATE Account
SET Balance = Balance - 500
WHERE AccountID = 101;

ROLLBACK;
```

---

## 6.6 SAVEPOINT

A savepoint creates an intermediate point to which a transaction can roll back.

```sql
START TRANSACTION;

UPDATE Account
SET Balance = Balance - 500
WHERE AccountID = 101;

SAVEPOINT P1;

UPDATE Account
SET Balance = Balance - 200
WHERE AccountID = 102;

ROLLBACK TO P1;

COMMIT;
```

---

## 6.7 Schedule

A **schedule** is the order in which operations from multiple transactions are executed.

### Serial Schedule

Transactions execute one after another without interleaving.

### Non-Serial Schedule

Operations from multiple transactions are interleaved.

A non-serial schedule may still be correct if it is serializable.

---

## 6.8 Conflicting Operations

Two operations conflict when:

1. They belong to different transactions.
2. They operate on the same data item.
3. At least one is a write.

### Conflicts

```text
Read-Read     → No conflict
Read-Write    → Conflict
Write-Read    → Conflict
Write-Write   → Conflict
```

---

## 6.9 Conflict Serializability

A schedule is conflict serializable if it is conflict-equivalent to some serial schedule.

### Precedence Graph

* Each transaction is represented by a node.
* Add `Ti → Tj` when a conflicting operation of `Ti` occurs before the conflicting operation of `Tj`.

### Result

```text
Acyclic graph → Conflict serializable
Cyclic graph  → Not conflict serializable
```

A topological ordering of an acyclic graph can provide an equivalent serial order.

---

## 6.10 Recoverability

### Recoverable Schedule

If `Tj` reads data written by `Ti`, then `Ti` must commit before `Tj` commits.

### Cascadeless Schedule

Transactions read only committed data.

This prevents cascading rollbacks caused by dirty reads.

### Strict Schedule

If a transaction writes an item, other transactions cannot read or write that item until the writing transaction commits or aborts.

### Relationship

```text
Strict
  ↓
Cascadeless
  ↓
Recoverable
```

---

## 6.11 View Serializability

View serializability considers:

* Initial reads
* Read-from relationships
* Final writes

Conflict-serializable schedules are always view-serializable, while the reverse is not necessarily true.

---

# 7. CONCURRENCY CONTROL

## 7.1 Purpose

Concurrency control ensures that simultaneous transaction execution maintains database correctness.

---

## 7.2 Common Concurrency Problems

### Lost Update

One transaction's update is overwritten by another transaction.

### Dirty Read

A transaction reads data written by another transaction that has not committed.

### Unrepeatable Read

The same row produces different values when read again because another transaction modified it.

### Phantom Read

Repeated execution of a range query returns a different set of rows because another transaction inserted, deleted, or otherwise changed qualifying rows.

---

## 7.3 Locks

### Shared Lock — S

Used for reading.

Multiple transactions may hold compatible shared locks simultaneously.

### Exclusive Lock — X

Used for writing.

An exclusive lock conflicts with shared and exclusive locks held by other transactions.

### Compatibility

| Existing / Requested |   S |  X |
| -------------------- | --: | -: |
| S                    | Yes | No |
| X                    |  No | No |

---

## 7.4 Two-Phase Locking — 2PL

2PL divides a transaction into two phases.

### Growing Phase

* Locks may be acquired.
* Locks are not released.

### Shrinking Phase

* Locks may be released.
* New locks are not acquired under standard 2PL.

2PL guarantees conflict serializability but does not by itself prevent deadlock.

---

## 7.5 Strict 2PL

Exclusive locks are held until the transaction commits or aborts.

This improves recoverability and prevents many cascading effects.

---

## 7.6 Rigorous 2PL

Both shared and exclusive locks are held until commit or abort.

Relationship:

```text
Rigorous 2PL
      ↓
 Strict 2PL
      ↓
      2PL
```

---

## 7.7 Deadlock

A deadlock occurs when transactions wait for one another in a cycle.

Example:

```text
T1 waits for T2
T2 waits for T1
```

---

## 7.8 Wait-For Graph

* Each transaction is a node.
* `Ti → Tj` means `Ti` is waiting for `Tj`.

A cycle indicates deadlock.

---

## 7.9 Wait-Die

Based on transaction timestamps:

* Older transaction requests a lock held by younger transaction → older transaction waits.
* Younger transaction requests a lock held by older transaction → younger transaction aborts.

---

## 7.10 Wound-Wait

* Older transaction requests a lock held by younger transaction → younger transaction is aborted.
* Younger transaction requests a lock held by older transaction → younger transaction waits.

---

## 7.11 Timestamp Ordering

Each transaction receives a unique timestamp.

Smaller timestamp generally means the transaction is older.

The system maintains values such as:

```text
ReadTS(X)
WriteTS(X)
```

Operations that violate the required timestamp order may cause a transaction to be rejected or restarted.

Timestamp ordering avoids lock-wait deadlocks because transactions do not wait for locks in the same way as lock-based protocols.

---

# 8. INDEXING & HASHING

## 8.1 Index

An index is an auxiliary data structure that helps locate records efficiently.

It maps search-key values to locations or pointers associated with records/pages.

---

## 8.2 Dense Index

A dense index contains an index entry for every search-key value or record, depending on the indexing scheme.

### Advantages

* Faster direct lookup
* More complete index information

### Disadvantage

* Requires more storage

---

## 8.3 Sparse Index

A sparse index contains fewer entries.

Sparse indexes generally require the underlying data to be ordered appropriately.

---

## 8.4 Primary Index

An index associated with the ordering/primary search key of the data file.

---

## 8.5 Secondary Index

An index built on a non-ordering attribute or another search key.

---

## 8.6 Multilevel Index

An index can itself be indexed.

This reduces the number of levels/pages that must be accessed during search.

---

## 8.7 B-Tree and B+ Tree

B-tree family structures are balanced multiway search trees.

### B+ Tree Structure

A typical B+ tree contains:

* Internal nodes containing search keys and child pointers
* Leaf nodes containing search-key entries and pointers to data records/pages
* Linked leaf nodes for ordered traversal

### Advantages

* Balanced height
* Efficient search
* Efficient insertion and deletion
* Efficient range queries
* Ordered traversal

---

## 8.8 B+ Tree Order

For a B+ tree of order `m`, a common convention is:

```text
Maximum children = m
Maximum keys in an internal node = m − 1
```

Minimum occupancy depends on the exact convention and implementation.

---

## 8.9 B+ Tree Search

The search follows one path from the root toward a leaf.

Approximate search complexity:

```text
O(logₘ N)
```

where `m` is the branching factor and `N` is the number of indexed entries.

---

## 8.10 B+ Tree Insertion

Typical process:

1. Locate the appropriate leaf.
2. Insert the key.
3. If overflow occurs, split the node.
4. Propagate the appropriate separator information upward.
5. A root split can increase tree height.

---

## 8.11 B+ Tree Deletion

Typical process:

1. Delete the key.
2. Check for underflow.
3. Redistribute from a suitable sibling when possible.
4. Otherwise merge nodes.
5. Adjust parent separator information.
6. A root merge can reduce tree height.

---

## 8.12 Hashing

Hashing maps a search key to a bucket using a hash function.

A simple hash function is:

```text
h(K) = K mod m
```

when this function is specified.

Example:

```text
K = 17
m = 5

h(17) = 17 mod 5 = 2
```

---

## 8.13 Collision

A collision occurs when two different keys map to the same bucket.

### Collision Handling

* Chaining
* Overflow buckets
* Open addressing, where applicable

---

## 8.14 B+ Tree vs Hash Index

| Property          | B+ Tree                | Hash                    |
| ----------------- | ---------------------- | ----------------------- |
| Equality search   | Efficient              | Very efficient          |
| Range search      | Efficient              | Generally poor          |
| Ordered traversal | Supported              | Not naturally supported |
| Structure         | Balanced tree          | Hash buckets            |
| Typical use       | Range + ordered access | Equality lookup         |

---

# 9. RELATIONAL ALGEBRA

## 9.1 Relational Algebra

Relational algebra is a procedural query language for the relational model.

It describes **how** to obtain a desired result.

---

## 9.2 Basic Operators

### Selection — σ

Selects rows satisfying a condition.

```text
σ Marks > 80 (Student)
```

Equivalent SQL idea:

```sql
SELECT *
FROM Student
WHERE Marks > 80;
```

---

### Projection — π

Selects required attributes.

```text
π Name, Marks (Student)
```

Equivalent SQL idea:

```sql
SELECT Name, Marks
FROM Student;
```

Classical relational algebra treats relations as sets, so projection removes duplicate tuples.

---

### Union — ∪

Combines tuples from two union-compatible relations.

```text
R ∪ S
```

---

### Difference — −

Returns tuples in the first relation but not in the second.

```text
R − S
```

Difference is directional.

---

### Cartesian Product — ×

Combines every tuple of one relation with every tuple of another.

If:

```text
|R| = m
|S| = n
```

then:

```text
|R × S| = m × n
```

---

### Rename — ρ

Renames a relation or its attributes.

Useful when the same relation is referenced more than once.

---

## 9.3 Joins

A join combines related tuples from relations.

### Theta Join

Uses an explicit comparison condition.

```text
R ⋈condition S
```

### Natural Join

Joins relations using common attributes and eliminates duplicate copies of common join attributes.

---

## 9.4 Division

Division is useful for queries involving **“for all”** conditions.

Conceptually:

```text
R ÷ S
```

returns values from `R` associated with every required value in `S`.

---

## 9.5 Relational Algebra and SQL

| Relational Algebra | SQL                    |
| ------------------ | ---------------------- |
| σ                  | WHERE                  |
| π                  | SELECT columns         |
| ∪                  | UNION                  |
| ∩                  | INTERSECT              |
| −                  | EXCEPT                 |
| ×                  | CROSS JOIN             |
| ⋈                  | JOIN                   |
| ρ                  | Alias / RENAME         |
| ÷                  | For-all query patterns |

---

## 9.6 Selection Pushdown

Selection operations can often be moved closer to the base relation.

Instead of:

```text
Join → Select
```

a query optimizer may use:

```text
Select → Join
```

when logically valid.

This reduces the number of tuples entering later operations.

---

# 10. QUERY PROCESSING & OPTIMIZATION

## 10.1 Query Processing Flow

```text
SQL Query
   ↓
Parsing / Translation
   ↓
Logical Representation
   ↓
Query Optimization
   ↓
Physical Execution Plan
   ↓
Execution
   ↓
Result
```

---

## 10.2 Parsing and Translation

The DBMS checks:

* SQL syntax
* Table and column names
* Data types
* Semantic validity
* Query structure

The query is translated into an internal representation.

---

## 10.3 Query Optimization

The optimizer searches for an efficient execution strategy among semantically equivalent alternatives.

### Important Cost Factors

* Disk I/O
* CPU processing
* Memory usage
* Intermediate result size
* Network cost in distributed systems

Disk/page I/O is often a major cost factor in database systems.

---

## 10.4 Query Tree

A query can be represented using a tree of relational operations.

Example:

```text
        π Name
           |
      σ Marks > 80
           |
        STUDENT
```

---

## 10.5 Selection Pushdown

Apply filters as early as possible when logically valid.

Example:

```text
Student JOIN Department
        ↓
   WHERE Marks > 80
```

can often be transformed into:

```text
σ Marks > 80(Student)
        JOIN
    Department
```

This can reduce intermediate results.

---

## 10.6 Projection Pushdown

Remove unnecessary columns as early as possible when they are not needed by later operations.

This reduces tuple width and intermediate storage requirements.

---

## 10.7 Join Algorithms

### Nested-Loop Join

For each tuple of one relation, tuples of the other relation are examined.

It is general but can become expensive.

### Indexed Nested-Loop Join

Uses an index on the inner relation's join attribute to find matching rows efficiently.

### Sort-Merge Join

Relations are sorted on the join attribute and then merged.

Useful when sorted data is already available or useful for later operations.

### Hash Join

Uses hashing to partition/build and probe matching tuples.

Particularly useful for equality joins.

---

## 10.8 Materialization

An intermediate result is fully computed and stored before the next operator consumes it.

### Advantages

* Intermediate result can be reused.
* Operator execution can be separated.

### Disadvantage

* Requires additional storage and I/O.

---

## 10.9 Pipelining

Tuples are passed directly from one operator to another without fully materializing the intermediate result.

### Advantages

* Reduces temporary storage
* Can reduce I/O
* Allows earlier result production

---

# 11. ENTITY-RELATIONSHIP MODEL

## 11.1 Entity

An entity is a distinguishable real-world object.

Examples:

* Student
* Employee
* Department
* Course

---

## 11.2 Entity Set

An entity set is a collection of similar entities.

Example:

```text
STUDENT
```

may contain all student entities.

---

## 11.3 Attributes

An attribute describes a property of an entity.

### Simple Attribute

Cannot be meaningfully divided into smaller components.

Example:

```text
Gender
```

### Composite Attribute

Can be divided into components.

Example:

```text
Name
├── FirstName
├── MiddleName
└── LastName
```

### Single-Valued Attribute

One value per entity.

### Multivalued Attribute

Multiple values per entity.

Example:

```text
PhoneNumbers
```

### Stored Attribute

Directly stored.

Example:

```text
DateOfBirth
```

### Derived Attribute

Calculated from another attribute.

Example:

```text
Age
```

derived from:

```text
DateOfBirth
```

### Key Attribute

An attribute used to uniquely identify an entity.

---

## 11.4 Relationship

A relationship represents an association between entity sets.

Example:

```text
STUDENT ─── ENROLLS ─── COURSE
```

---

## 11.5 Relationship Degree

### Unary Relationship

Involves one entity set.

Example:

```text
Employee manages Employee
```

### Binary Relationship

Involves two entity sets.

Example:

```text
Student enrolls in Course
```

### Ternary Relationship

Involves three entity sets.

---

## 11.6 Cardinality

### One-to-One

```text
1 : 1
```

### One-to-Many

```text
1 : N
```

### Many-to-One

```text
N : 1
```

### Many-to-Many

```text
M : N
```

---

## 11.7 Participation

### Total Participation

Every entity must participate in the relationship.

### Partial Participation

Participation is optional for some entities.

---

## 11.8 Weak Entity

A weak entity cannot be uniquely identified by its own attributes alone.

It depends on an owner/strong entity.

Typical characteristics:

* Does not have a complete key of its own
* Has a partial key
* Has total participation in the identifying relationship
* Traditionally represented using a double rectangle
* Identifying relationship traditionally represented using a double diamond

---

## 11.9 Relationship Attributes

Some attributes belong to a relationship rather than an individual entity.

Example:

```text
STUDENT ─── ENROLLS ─── COURSE
                  |
                Grade
```

`Grade` describes the enrollment relationship.

---

## 11.10 Specialization and Generalization

### Specialization

Top-down approach.

A general entity is divided into more specific subclasses.

Example:

```text
Employee
   ├── Faculty
   └── Staff
```

### Generalization

Bottom-up approach.

Common characteristics of multiple entities are combined into a generalized entity.

---

## 11.11 Disjoint and Overlapping Constraints

### Disjoint

An entity can belong to at most one subclass.

### Overlapping

An entity may belong to multiple subclasses.

---

## 11.12 Total and Partial Specialization

### Total Specialization

Every superclass entity must belong to a subclass.

### Partial Specialization

Some superclass entities may belong to no subclass.

---

## 11.13 ER to Relational Mapping

### Strong Entity

Map to a relation.

```text
EMPLOYEE(EmployeeID, Name, Salary)
```

### Composite Attribute

Store its component attributes.

```text
Name → FirstName, LastName
```

### Multivalued Attribute

Create a separate relation.

```text
EmployeePhone(EmployeeID, Phone)
```

### 1:N Relationship

Place the primary key of the 1-side as a foreign key in the N-side.

```text
DEPARTMENT(DeptID, DeptName)

EMPLOYEE(EmployeeID, Name, DeptID)
```

### M:N Relationship

Create a separate relation.

```text
ENROLLMENT(StudentID, CourseID, Grade)
```

The relation contains the keys of participating entities and any relationship attributes.

---

# 12. DATABASE RECOVERY

## 12.1 Purpose of Recovery

Database recovery restores the database to a correct and consistent state after failures.

---

## 12.2 Types of Failures

### Transaction Failure

A transaction cannot complete successfully.

Possible causes include:

* Constraint violation
* Logical error
* Explicit rollback

### System Failure

A crash or power failure causes loss of volatile state.

### Media Failure

Storage media is damaged or data becomes inaccessible.

---

## 12.3 Log-Based Recovery

A log records transaction activity.

Example:

```text
<T1 START>
<T1, A, old_value, new_value>
<T1 COMMIT>
```

The exact format depends on the recovery system.

---

## 12.4 Write-Ahead Logging — WAL

The write-ahead logging principle requires the necessary log record to reach stable storage before the corresponding modified database page is written to stable storage.

This allows recovery information to be available before the database page itself is persisted.

---

## 12.5 UNDO

UNDO restores the previous value.

Example:

```text
Old value = 500
New value = 300
```

UNDO restores:

```text
500
```

---

## 12.6 REDO

REDO reapplies a committed change.

Example:

```text
Old value = 500
New value = 300
```

REDO ensures the intended new value:

```text
300
```

is reflected after recovery.

---

## 12.7 Deferred Update

Database changes are delayed until transaction commit under the basic deferred-update model.

Recovery generally requires **REDO** for committed transactions because uncommitted changes have not been applied to the database.

---

## 12.8 Immediate Update

Database changes may be written before transaction commit.

Therefore recovery may require:

```text
UNDO + REDO
```

depending on the recovery protocol.

---

## 12.9 Checkpoint

A checkpoint records a recovery point and reduces the amount of log that normally needs to be examined during recovery.

A checkpoint reduces recovery work but does not eliminate the need for recovery.

---

## 12.10 Cascading Rollback

A cascading rollback occurs when a transaction must be rolled back because it depended on data written by another transaction that subsequently failed.

This can occur when transactions read uncommitted data.

Cascadeless execution prevents transactions from reading uncommitted writes.

---

## 12.11 Shadow Paging

Shadow paging maintains:

* A shadow page table
* A current page table

The shadow structure provides a stable reference to the previous database state while updates are made through the current structure.

---

# 13. STORAGE & FILE ORGANIZATION

## 13.1 Storage Hierarchy

A simplified storage hierarchy is:

```text
CPU Registers
     ↓
Cache
     ↓
Main Memory / RAM
     ↓
SSD / Disk
```

Higher levels generally provide faster access but have smaller capacity.

---

## 13.2 Pages and Blocks

A DBMS commonly transfers data between secondary storage and memory in units such as:

* Pages
* Blocks

Database operations are therefore heavily influenced by the number of page/block transfers required.

---

## 13.3 Record

A record is the storage representation of a tuple/row.

Example:

```text
101 | Rahul | 85 | CSE
```

---

## 13.4 Fixed-Length Records

All records have the same size.

### Advantages

* Simple storage management
* Easy address calculation
* Fast access

---

## 13.5 Variable-Length Records

Records can have different sizes.

They may require:

* Length information
* Offset information
* Slot directories
* Additional record-management metadata

---

## 13.6 Slotted Page

A slotted page is a page organization commonly used for variable-length records.

A simplified structure:

```text
+----------------------+
| Page Header          |
+----------------------+
| Record Data          |
| Record Data          |
|                      |
| Free Space           |
|                      |
+----------------------+
| Slot Directory       |
+----------------------+
```

The slot directory helps locate records within the page.

---

## 13.7 Spanned Records

A record is **spanned** when it is allowed to cross a page boundary.

Example:

```text
Page 1: [part of record]
Page 2: [remaining part]
```

---

## 13.8 Unspanned Records

A record must fit entirely within one page.

---

## 13.9 File Organization

### Heap File

Records are stored without a specific ordering.

Advantages:

* Simple
* Efficient insertion

Searching may require scanning many records.

---

### Sequential / Ordered File

Records are maintained in a specified order.

Advantages:

* Efficient sequential access
* Useful for ordered/range processing

Insertions may require additional work.

---

### Hash File

Records are organized using a hash function.

Advantages:

* Efficient equality search

Generally unsuitable for ordered range access.

---

### Clustered Organization

Related records are stored physically close together to improve locality for related access patterns.

---

## 13.10 Buffer Manager

The buffer manager manages database pages between disk/storage and main memory.

Responsibilities include:

* Fetching pages
* Managing memory frames
* Tracking page usage
* Selecting pages for replacement
* Writing modified pages back to storage

---

## 13.11 Buffer Hit and Buffer Miss

### Buffer Hit

Requested page is already present in memory.

No storage read is required.

### Buffer Miss

Requested page is not present in memory.

The DBMS must fetch it from storage.

---

## 13.12 Dirty Page

A dirty page is a buffer page that has been modified in memory but whose latest contents have not yet been written to the corresponding stable-storage location.

---

## 13.13 Blocking Factor

The blocking factor represents the number of records that fit in one block.

For fixed-length records:

```text
bfr = floor(Block Size / Record Size)
```

### Example

Given:

```text
Block size = 1000 bytes
Record size = 120 bytes
```

Then:

```text
bfr = floor(1000 / 120)
    = floor(8.333...)
    = 8 records/block
```

---

## 13.14 Number of Blocks

If there are `r` records and the blocking factor is `bfr`:

```text
Number of blocks = ceil(r / bfr)
```

### Example

```text
Records = 950
bfr = 8
```

Therefore:

```text
Blocks = ceil(950 / 8)
       = ceil(118.75)
       = 119
```
