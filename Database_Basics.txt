1. DBMS FUNDAMENTALS & ARCHITECTURE
1.1 Database

A database is an organized collection of related data that can be efficiently stored, accessed, and managed.

1.2 DBMS

A Database Management System (DBMS) is software used to:

Create databases
Store data
Retrieve data
Update data
Delete data
Manage security
Maintain integrity
Handle concurrent users
Provide backup and recovery
1.3 File System vs DBMS
File System	DBMS

2.2 Keys
Super Key

Any set of attributes that uniquely identifies a tuple.

It may contain unnecessary attributes.

Candidate Key

A minimal super key.

Primary Key

Candidate key selected as the main key.

Only one primary key constraint is selected for a relation, though it can contain multiple attributes.

Alternate Key

Candidate key not selected as primary key.

Foreign Key

Attribute(s) referencing a candidate/primary key of another relation.

Composite Key

Key consisting of more than one attribute.

2.3 Example

RollNo

3. FUNCTIONAL DEPENDENCIES & ATTRIBUTE CLOSURE
3.1 Functional Dependency

An FD:

$$ X\rightarrow Y $$

means:

If two tuples have the same X value, they must have the same Y value.

X = determinant.

3.2 Types
Trivial FD
$$ X\rightarrow Y $$

where:

$$ Y\subseteq X $$

Example:

$$ AB\rightarrow A $$
Non-trivial FD
$$ Y\nsubseteq X $$
Completely Non-trivial
$$ X\cap Y=\emptyset $$
3.3 Armstrong's Axioms ⭐⭐⭐⭐⭐
Reflexivity

If:

$$ Y\subseteq X $$

then:

$$ X\rightarrow Y $$
Augmentation

If:

$$ X\rightarrow Y $$

then:

$$ XZ\rightarrow YZ $$
Transitivity

If:

$$ X\rightarrow Y $$

and

$$ Y\rightarrow Z $$

then:

$$ X\rightarrow Z $$
Derived Rules
Union
$$ X\rightarrow Y,\ X\rightarrow Z $$

then:

$$ X\rightarrow YZ $$
Decomposition
$$ X\rightarrow YZ $$

then:

$$ X\rightarrow Y $$

and:

$$ X\rightarrow Z $$
Pseudotransitivity

If:

$$ X\rightarrow Y $$

and:

$$ WY\rightarrow Z $$

then:

$$ WX\rightarrow Z $$
3.4 Attribute Closure ⭐⭐⭐⭐⭐

\(X^+\) = all attributes functionally determined by X.

Candidate-key method
Find attributes that don't appear on RHS.
They must be included in every candidate key.
Compute closure.
If closure contains all attributes → super key.
Check minimality → candidate key.
Example
$$ R(A,B,C,D,E) $$

FDs:

$$ A\rightarrow B $$ $$ B\rightarrow C $$ $$ CD\rightarrow E $$

Consider:

$$ AD^+ $$

Start:

AD

A→B:

ABD

B→C:

ABCD

CD→E:

ABCDE

Therefore:

$$ AD^+=ABCDE $$

So AD is a super key.

If minimal:

$$ \boxed{AD=\text{Candidate Key}} $$
🔥 FD Traps
A→B does NOT imply B→A.
Determinant is not automatically a candidate key.
Closure must cover all attributes.
Candidate key must be minimal.
Attributes not appearing on RHS must be included in every candidate key under the standard setup.
Candidate key → super key.
Super key → not necessarily candidate key.

5. NORMALIZATION
5.1 Purpose

Normalization reduces:

Redundancy
Update anomaly
Insertion anomaly
Deletion anomaly
5.2 1NF

A relation is in 1NF if attributes contain atomic values and there are no repeating groups.

Does 1NF guarantee no redundancy?

No.

5.3 2NF ⭐⭐⭐⭐⭐

Requirements:

Relation is in 1NF.
No partial dependency of a non-prime attribute on a candidate key.
Partial Dependency

Suppose candidate key:

$$ AB $$

and:

$$ A\rightarrow C $$

where C is non-prime.

Then partial dependency exists.

Important shortcut

If all candidate keys are single-attribute, then partial dependency cannot occur.

Therefore:

A 1NF relation with only single-attribute candidate keys is automatically in 2NF.

5.4 Prime Attribute

An attribute that belongs to at least one candidate key.

Non-prime

Doesn't belong to any candidate key.

5.5 3NF ⭐⭐⭐⭐⭐

For every non-trivial FD:

$$ X\rightarrow A $$

at least one must hold:

X is a super key, OR
A is a prime attribute.
5.6 BCNF ⭐⭐⭐⭐⭐

For every non-trivial FD:

$$ X\rightarrow Y $$

X must be a super key.

Shortcut
3NF:
X is superkey OR RHS is prime

BCNF:
X MUST be superkey
5.7 3NF vs BCNF

BCNF is stricter than 3NF.

A relation can be:

3NF but NOT BCNF
5.8 Classic Example
$$ R(Student, Course, Instructor) $$

FDs:

$$ Course\rightarrow Instructor $$ $$ Instructor\rightarrow Course $$

Candidate keys:

Student + Course
Student + Instructor

Course and Instructor are prime attributes.

Thus 3NF can hold even though Course/Instructor may not be superkeys.

BCNF fails.

5.9 Lossless Decomposition

A decomposition is lossless if joining decomposed relations reconstructs the original relation without spurious tuples.

For binary decomposition:

$$ R\rightarrow R_1,R_2 $$

a common condition is:

$$ (R_1\cap R_2)\rightarrow R_1 $$

or

$$ (R_1\cap R_2)\rightarrow R_2 $$

under \(F^+\).

5.10 Dependency Preservation

A decomposition is dependency preserving if the original dependencies can be enforced using the decomposed relations without requiring joins.

🔥 Trap
Lossless ≠ Dependency Preserving
🔥 NORMALIZATION TRAPS
1NF → atomic values.
2NF → no partial dependency.
3NF → superkey OR prime RHS.
BCNF → every determinant is a superkey.
Partial dependency requires composite candidate key.
Single-attribute keys → no partial dependency.
Prime = belongs to candidate key.
BCNF stronger than 3NF.
3NF can be not BCNF.
Need candidate keys before deciding normal form.
Lossless and dependency preservation are different properties.








6. TRANSACTIONS & SERIALIZABILITY
6.1 Transaction

A transaction is a logical unit of database operations.

6.2 ACID ⭐⭐⭐⭐⭐
Atomicity

All operations or none.

Consistency

Valid database state → valid database state.

Isolation

Concurrent transactions behave appropriately, ideally as if executed serially according to the chosen isolation/serializability guarantees.

Durability

Committed effects survive failures.

6.3 Transaction States
Active
 ↓
Partially Committed
 ↓
Committed

Failure:

Active
 ↓
Failed
 ↓
Aborted
6.4 Schedule

A schedule is an ordering/interleaving of operations from transactions that preserves each transaction's internal order.

Serial Schedule

Transactions execute one after another.

Non-Serial

Operations are interleaved.

Important
Non-serial ≠ Non-serializable

A nonserial schedule can still be serializable.

6.5 Conflicting Operations ⭐⭐⭐⭐⭐

Two operations conflict if:

They belong to different transactions.
They operate on the same data item.
At least one is a write.

Therefore:

RR → No conflict
RW → Conflict
WR → Conflict
WW → Conflict
6.6 Precedence Graph

Create:

One node per transaction

Add:

$$ T_i\rightarrow T_j $$

if a conflicting operation of Ti occurs before Tj.

Result:
Acyclic graph
→ Conflict serializable

Cycle
→ NOT conflict serializable
6.7 Serial Order

If graph is acyclic, perform topological ordering.

The topological order gives an equivalent serial order.

6.8 Recoverable Schedule

If Tj reads data written by Ti:

$$ Ti \text{ must commit before } Tj $$
6.9 Cascadeless

Transactions read only values written by committed transactions.

6.10 Strict

If Ti writes X, no other transaction can read/write X until Ti commits or aborts.

Relationship:

$$ \boxed{Strict\Rightarrow Cascadeless\Rightarrow Recoverable} $$
6.11 View Serializability

Conflict serializability is more restrictive.

$$ Conflict\ Serializable \Rightarrow View\ Serializable $$

Reverse is not necessarily true.

🔥 TRANSACTION TRAPS
Serial schedule → conflict serializable.
Nonserial doesn't mean nonserializable.
RR → no conflict.
RW/WR/WW → conflict.
Same data item is required.
Cycle → not conflict serializable.
Acyclic → conflict serializable.
Topological order → serial order.
Recoverable → commit dependency.
Cascadeless → read only committed writes.
Strict → prevents reads/writes of uncommitted written item.
Strict ⇒ Cascadeless ⇒ Recoverable.
Conflict serializable ⇒ View serializable.






7. CONCURRENCY CONTROL
7.1 Problems
Lost Update

One transaction's update gets overwritten.

Dirty Read

Reading uncommitted data.

Unrepeatable Read

Same row gives different values when read again.

Phantom Read

Repeated query returns a different set of rows because another transaction inserted/deleted matching rows.

7.2 Locks
Shared Lock (S)

Used for reading.

Multiple S locks can coexist.

Exclusive Lock (X)

Used for writing.

X is incompatible with S and X.

7.3 Compatibility
	S	X
S	✅	❌
X	❌	❌
7.4 Two-Phase Locking (2PL)
Growing Phase

Acquire locks.

Shrinking Phase

Release locks.

After the first lock is released:

No new lock can be acquired under standard 2PL.

2PL guarantees conflict serializability but can cause deadlocks.

7.5 Strict 2PL

Holds X locks until commit/abort.

7.6 Rigorous 2PL

Holds both S and X locks until commit/abort.

Relationship:

$$ \boxed{Rigorous\Rightarrow Strict\Rightarrow 2PL} $$
7.7 Deadlock

Transactions wait for each other indefinitely.

Wait-for graph:

T1 → T2
T2 → T1

Cycle = deadlock.

7.8 Wait-Die ⭐⭐⭐⭐⭐

Older transaction requests younger's lock:

Older → waits

Younger requests older's lock:

Younger → dies/aborts
Memory

Wait-Die: Older waits, younger dies.

7.9 Wound-Wait

Older requests younger's resource:

Younger → aborted/wounded

Younger requests older's resource:

Younger → waits
Memory

Wound-Wait: Older wounds, younger waits.

7.10 Timestamp Ordering

Each transaction gets a timestamp.

Smaller timestamp:

Older transaction.

Maintain:

ReadTS(X)
WriteTS(X)

Basic timestamp ordering aborts a transaction when an operation violates the required timestamp order.

🔥 CONCURRENCY TRAPS
S-S compatible.
S-X incompatible.
X-X incompatible.
2PL → growing + shrinking.
After releasing first lock → no new lock under standard 2PL.
2PL guarantees conflict serializability.
2PL can still deadlock.
Strict 2PL → X locks till commit/abort.
Rigorous → S and X till commit/abort.
Rigorous ⇒ Strict ⇒ 2PL.
Wait-for cycle → deadlock.
Wait-Die → older waits, younger dies.
Wound-Wait → older wounds, younger waits.
Smaller timestamp → older.
Timestamp ordering avoids lock-wait deadlocks.

An index maps a search key to locations/pointers for finding records more efficiently.

8.2 Dense Index

Advantage

Disadvantage

8.3 Sparse Index

🔥 Trap

8.4 Primary vs Secondary Index

Typically associated with the ordering/primary search key.

8.5 Multilevel Index

Top Index
   ↓

   ↓

8.6 B-Tree / B+ Tree

Balanced multiway trees.

8.7 B+ Tree ⭐⭐⭐⭐⭐

Important properties:

Internal nodes contain search keys and child pointers.
Actual data-record pointers are at leaf level in the common DBMS representation.
Leaf nodes are linked.
Balanced tree.
Good for range queries.
8.8 B+ Tree Order

For order \(m\):

$$ \boxed{\text{Maximum children}=m} $$

and:

$$ \boxed{\text{Maximum keys}=m-1} $$

Minimum occupancy depends on the exact convention/question.

Root is a special case.
8.9 B+ Tree Search

$$ O(\log_m N) $$
8.10 B+ Tree Insertion

 ↓

 ↓
Propagate separator

8.11 Deletion

or

8.12 Hashing

Example:

$$ h(K)=K\bmod m $$

$$ K=17,\ m=5 $$

$$ h(17)=2 $$
8.13 Collision

8.14 B+ Tree vs Hash

Ordered	Not inherently ordered

12. DATABASE RECOVERY
12.1 Purpose

Recovery restores the database to a consistent state after failures.

12.2 Failure Types
Transaction Failure

Individual transaction fails.

System Crash

Volatile memory contents may be lost.

Media Failure

Storage itself is damaged.

May require:

Backup + Recovery
12.3 Log-Based Recovery

Log records changes.

Example:

<T1, START>
<T1, A, old, new>
<T1, COMMIT>
12.4 Write-Ahead Logging (WAL) ⭐⭐⭐⭐⭐

Rule:

Log record must reach stable storage before the corresponding modified data page is written.

Transaction
 ↓
Log
 ↓
Stable Storage
 ↓
Data Page

Before commit is acknowledged, necessary commit log information must be safely stored according to the recovery protocol.

12.5 UNDO

Restore old value.

Old = 100
New = 50

UNDO → 100
12.6 REDO

Reapply new value.

Old = 100
New = 50

REDO → 50
12.7 Deferred Update ⭐⭐⭐⭐⭐

Database modification is delayed until commit.

Generally:

$$ \boxed{Deferred\rightarrow REDO} $$

No database changes from an uncommitted transaction need to be undone because they haven't been installed in the database under the basic deferred-update model.

12.8 Immediate Update ⭐⭐⭐⭐⭐

Database may be modified before commit.

Therefore:

$$ \boxed{Immediate\rightarrow UNDO+REDO} $$
12.9 Checkpoint

Reduces recovery work.

Earlier log
   ↓
CHECKPOINT
   ↓
Later log
   ↓
Crash

Checkpoint does not mean failures cannot happen.

12.10 Cascading Rollback

Example:

T1 writes A
T2 reads A
T1 aborts

T2 may also need rollback.

12.11 Cascadeless

A transaction reads only values written by committed transactions.

12.12 Shadow Paging

Uses:

Shadow page table
Current page table

Alternative recovery technique to traditional log-based recovery.

🔥 RECOVERY TRAPS
WAL → log first, corresponding data page later.
WAL doesn't mean data first.
Deferred → generally REDO.
Immediate → UNDO + REDO.
UNDO → old value.
REDO → new value.
Checkpoint → reduces recovery work.
Checkpoint doesn't eliminate recovery.
Dirty read can cause cascading rollback.
Cascadeless prevents reading uncommitted writes.
Strict is stronger than cascadeless.
Serializability ≠ recovery.
Shadow paging uses shadow/current page tables.










13. STORAGE & FILE ORGANIZATION
13.1 Storage Hierarchy
Registers
 ↓
Cache
 ↓
RAM
 ↓
SSD/Disk

Database data is commonly transferred between storage and memory in pages/blocks.

13.2 Page / Block

Basic unit of disk-memory transfer.

Example:

Page
 ├── Header
 ├── Records
 └── Free Space
13.3 Record

One tuple/row.

13.4 Fixed-Length Record

All records same size.

Formula:

$$ \boxed{ Records/Page= \left\lfloor \frac{Usable\ Page\ Size}{Record\ Size} \right\rfloor } $$
13.5 Variable-Length Record

Records can have different lengths.

Often requires:

Offsets
Lengths
Slot directory
13.6 Slotted Page ⭐⭐⭐⭐⭐

Common structure:

┌──────────────────┐
│ Page Header      │
├──────────────────┤
│ Record 1         │
│ Record 2         │
│ Record 3         │
│                  │
│ Free Space       │
├──────────────────┤
│ Slot Directory   │
└──────────────────┘

Useful for variable-length records.

13.7 Spanned vs Unspanned
Spanned

Record can cross page boundaries.

Unspanned

Record must stay within one page.

Spanned   → Can cross
Unspanned → Cannot cross
13.8 Heap Organization

Records unordered.

Good for:
Insertion
Bad for:

Searching without an index.

13.9 Sequential / Ordered

Records stored according to ordering key.

Good for:
Sequential processing
Ordered access
Range queries
13.10 Hash Organization
$$ h(K)=K\bmod m $$

Good for equality.

Poor for range.

13.11 Buffer Manager

Manages pages between storage and RAM.

Responsibilities:

Fetch pages
Manage buffer frames
Replace pages
Write modified pages back
13.12 Buffer Hit

Page already in buffer.

No disk read required.

Buffer Miss

Page not present.

Requires fetching from storage.

13.13 Dirty Page

Page modified in memory compared with its stored version.

13.14 Blocking Factor ⭐⭐⭐⭐⭐

If:

Block size = B
Record size = R

then:

$$ \boxed{ bfr=\left\lfloor\frac{B}{R}\right\rfloor } $$
13.15 Number of Blocks

If:

Number of records = r
Blocking factor = bfr

then:

$$ \boxed{ b=\left\lceil\frac{r}{bfr}\right\rceil } $$
🔥 Critical shortcut
Records per block → FLOOR
Number of blocks → CEILING
Example

Block = 1000 bytes.

Record = 120 bytes.

$$ bfr=\lfloor1000/120\rfloor=8 $$

For 950 records:

$$ blocks=\lceil950/8\rceil=119 $$
