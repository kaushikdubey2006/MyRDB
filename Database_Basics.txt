1. DBMS FUNDAMENTALS & ARCHITECTURE
1.1 Database

A database is an organized collection of related data that can be efficiently stored, accessed, and managed.

1.2 DBMS

A Database Management System (DBMS) is software used to:

Create databases
Store data
Retrieve data
Update data
Delete data
Manage security
Maintain integrity
Handle concurrent users
Provide backup and recovery
1.3 File System vs DBMS
File System	DBMS
Data redundancy is common	Redundancy can be controlled
Limited security	Better security
Difficult concurrency control	Concurrency control
Limited recovery	Backup/recovery mechanisms
Program-data dependence	Data independence
Difficult complex queries	SQL/query processing
1.4 Three-Level Architecture ⭐⭐⭐⭐⭐
External Level
(View Level)
      ↓
Conceptual Level
(Logical Level)
      ↓
Internal Level
(Physical Level)
External Level

What individual users/applications see.

Conceptual Level

Overall logical structure of the database.

Internal Level

How data is physically stored.

1.5 Data Independence ⭐⭐⭐⭐⭐
Physical Data Independence

Changes at internal/physical level without changing conceptual schema.

Example:

Change indexing/storage
        ↓
Logical schema unchanged
Logical Data Independence

Changes to conceptual schema without requiring changes to external views/programs.

🔥 Trap
Physical DI → Internal changes
Logical DI  → Conceptual changes
1.6 Schema vs Instance
Schema

Structure/design of database.

Instance

Actual data present at a particular moment.

Schema → relatively stable
Instance → changes frequently
1.7 DBA

Database Administrator responsibilities include:

Authorization
Security
Backup
Recovery
Performance monitoring
Storage management
Database maintenance
🔥 Traps
Internal level → physical storage.
Physical DI → internal-level changes.
Logical DI → conceptual-level changes.
Instance changes frequently.
DBA handles authorization, backup and recovery.









2. RELATIONAL MODEL, KEYS & CONSTRAINTS
2.1 Basic Terms
Term	Meaning
Relation	Table
Tuple	Row
Attribute	Column
Domain	Allowed set of values
Degree	Number of attributes
Cardinality	Number of tuples
🔥 Shortcut
Degree → Columns
Cardinality → Rows
2.2 Keys
Super Key

Any set of attributes that uniquely identifies a tuple.

It may contain unnecessary attributes.

Candidate Key

A minimal super key.

Primary Key

Candidate key selected as the main key.

Only one primary key constraint is selected for a relation, though it can contain multiple attributes.

Alternate Key

Candidate key not selected as primary key.

Foreign Key

Attribute(s) referencing a candidate/primary key of another relation.

Composite Key

Key consisting of more than one attribute.

2.3 Example

Suppose:

STUDENT(RollNo, Email, Name, Phone)

If both RollNo and Email uniquely identify students:

Candidate keys:
RollNo
Email

If RollNo is selected:

Primary key = RollNo
Alternate key = Email
2.4 Integrity Constraints
Domain Integrity

Values must belong to the valid domain.

Entity Integrity

Primary key cannot be NULL.

Referential Integrity

Foreign key must reference a valid key value, subject to the allowed NULL/action rules.

Key Constraint

Key values must uniquely identify tuples.

🔥 Key Traps
Every candidate key is a super key.
Every super key is not necessarily a candidate key.
Candidate key = minimal super key.
Primary key = selected candidate key.
Multiple candidate keys can exist.
Entity integrity → PK cannot be NULL.
Referential integrity → FK references a valid key.
FK may contain NULL unless restricted by NOT NULL.
Degree → columns.
Cardinality → rows.
















3. FUNCTIONAL DEPENDENCIES & ATTRIBUTE CLOSURE
3.1 Functional Dependency

An FD:

$$ X\rightarrow Y $$

means:

If two tuples have the same X value, they must have the same Y value.

X = determinant.

3.2 Types
Trivial FD
$$ X\rightarrow Y $$

where:

$$ Y\subseteq X $$

Example:

$$ AB\rightarrow A $$
Non-trivial FD
$$ Y\nsubseteq X $$
Completely Non-trivial
$$ X\cap Y=\emptyset $$
3.3 Armstrong's Axioms ⭐⭐⭐⭐⭐
Reflexivity

If:

$$ Y\subseteq X $$

then:

$$ X\rightarrow Y $$
Augmentation

If:

$$ X\rightarrow Y $$

then:

$$ XZ\rightarrow YZ $$
Transitivity

If:

$$ X\rightarrow Y $$

and

$$ Y\rightarrow Z $$

then:

$$ X\rightarrow Z $$
Derived Rules
Union
$$ X\rightarrow Y,\ X\rightarrow Z $$

then:

$$ X\rightarrow YZ $$
Decomposition
$$ X\rightarrow YZ $$

then:

$$ X\rightarrow Y $$

and:

$$ X\rightarrow Z $$
Pseudotransitivity

If:

$$ X\rightarrow Y $$

and:

$$ WY\rightarrow Z $$

then:

$$ WX\rightarrow Z $$
3.4 Attribute Closure ⭐⭐⭐⭐⭐

\(X^+\) = all attributes functionally determined by X.

Candidate-key method
Find attributes that don't appear on RHS.
They must be included in every candidate key.
Compute closure.
If closure contains all attributes → super key.
Check minimality → candidate key.
Example
$$ R(A,B,C,D,E) $$

FDs:

$$ A\rightarrow B $$ $$ B\rightarrow C $$ $$ CD\rightarrow E $$

Consider:

$$ AD^+ $$

Start:

AD

A→B:

ABD

B→C:

ABCD

CD→E:

ABCDE

Therefore:

$$ AD^+=ABCDE $$

So AD is a super key.

If minimal:

$$ \boxed{AD=\text{Candidate Key}} $$
🔥 FD Traps
A→B does NOT imply B→A.
Determinant is not automatically a candidate key.
Closure must cover all attributes.
Candidate key must be minimal.
Attributes not appearing on RHS must be included in every candidate key under the standard setup.
Candidate key → super key.
Super key → not necessarily candidate key.

5. NORMALIZATION
5.1 Purpose

Normalization reduces:

Redundancy
Update anomaly
Insertion anomaly
Deletion anomaly
5.2 1NF

A relation is in 1NF if attributes contain atomic values and there are no repeating groups.

Does 1NF guarantee no redundancy?

No.

5.3 2NF ⭐⭐⭐⭐⭐

Requirements:

Relation is in 1NF.
No partial dependency of a non-prime attribute on a candidate key.
Partial Dependency

Suppose candidate key:

$$ AB $$

and:

$$ A\rightarrow C $$

where C is non-prime.

Then partial dependency exists.

Important shortcut

If all candidate keys are single-attribute, then partial dependency cannot occur.

Therefore:

A 1NF relation with only single-attribute candidate keys is automatically in 2NF.

5.4 Prime Attribute

An attribute that belongs to at least one candidate key.

Non-prime

Doesn't belong to any candidate key.

5.5 3NF ⭐⭐⭐⭐⭐

For every non-trivial FD:

$$ X\rightarrow A $$

at least one must hold:

X is a super key, OR
A is a prime attribute.
5.6 BCNF ⭐⭐⭐⭐⭐

For every non-trivial FD:

$$ X\rightarrow Y $$

X must be a super key.

Shortcut
3NF:
X is superkey OR RHS is prime

BCNF:
X MUST be superkey
5.7 3NF vs BCNF

BCNF is stricter than 3NF.

A relation can be:

3NF but NOT BCNF
5.8 Classic Example
$$ R(Student, Course, Instructor) $$

FDs:

$$ Course\rightarrow Instructor $$ $$ Instructor\rightarrow Course $$

Candidate keys:

Student + Course
Student + Instructor

Course and Instructor are prime attributes.

Thus 3NF can hold even though Course/Instructor may not be superkeys.

BCNF fails.

5.9 Lossless Decomposition

A decomposition is lossless if joining decomposed relations reconstructs the original relation without spurious tuples.

For binary decomposition:

$$ R\rightarrow R_1,R_2 $$

a common condition is:

$$ (R_1\cap R_2)\rightarrow R_1 $$

or

$$ (R_1\cap R_2)\rightarrow R_2 $$

under \(F^+\).

5.10 Dependency Preservation

A decomposition is dependency preserving if the original dependencies can be enforced using the decomposed relations without requiring joins.

🔥 Trap
Lossless ≠ Dependency Preserving
🔥 NORMALIZATION TRAPS
1NF → atomic values.
2NF → no partial dependency.
3NF → superkey OR prime RHS.
BCNF → every determinant is a superkey.
Partial dependency requires composite candidate key.
Single-attribute keys → no partial dependency.
Prime = belongs to candidate key.
BCNF stronger than 3NF.
3NF can be not BCNF.
Need candidate keys before deciding normal form.
Lossless and dependency preservation are different properties.








6. TRANSACTIONS & SERIALIZABILITY
6.1 Transaction

A transaction is a logical unit of database operations.

6.2 ACID ⭐⭐⭐⭐⭐
Atomicity

All operations or none.

Consistency

Valid database state → valid database state.

Isolation

Concurrent transactions behave appropriately, ideally as if executed serially according to the chosen isolation/serializability guarantees.

Durability

Committed effects survive failures.

6.3 Transaction States
Active
 ↓
Partially Committed
 ↓
Committed

Failure:

Active
 ↓
Failed
 ↓
Aborted
6.4 Schedule

A schedule is an ordering/interleaving of operations from transactions that preserves each transaction's internal order.

Serial Schedule

Transactions execute one after another.

Non-Serial

Operations are interleaved.

Important
Non-serial ≠ Non-serializable

A nonserial schedule can still be serializable.

6.5 Conflicting Operations ⭐⭐⭐⭐⭐

Two operations conflict if:

They belong to different transactions.
They operate on the same data item.
At least one is a write.

Therefore:

RR → No conflict
RW → Conflict
WR → Conflict
WW → Conflict
6.6 Precedence Graph

Create:

One node per transaction

Add:

$$ T_i\rightarrow T_j $$

if a conflicting operation of Ti occurs before Tj.

Result:
Acyclic graph
→ Conflict serializable

Cycle
→ NOT conflict serializable
6.7 Serial Order

If graph is acyclic, perform topological ordering.

The topological order gives an equivalent serial order.

6.8 Recoverable Schedule

If Tj reads data written by Ti:

$$ Ti \text{ must commit before } Tj $$
6.9 Cascadeless

Transactions read only values written by committed transactions.

6.10 Strict

If Ti writes X, no other transaction can read/write X until Ti commits or aborts.

Relationship:

$$ \boxed{Strict\Rightarrow Cascadeless\Rightarrow Recoverable} $$
6.11 View Serializability

Conflict serializability is more restrictive.

$$ Conflict\ Serializable \Rightarrow View\ Serializable $$

Reverse is not necessarily true.

🔥 TRANSACTION TRAPS
Serial schedule → conflict serializable.
Nonserial doesn't mean nonserializable.
RR → no conflict.
RW/WR/WW → conflict.
Same data item is required.
Cycle → not conflict serializable.
Acyclic → conflict serializable.
Topological order → serial order.
Recoverable → commit dependency.
Cascadeless → read only committed writes.
Strict → prevents reads/writes of uncommitted written item.
Strict ⇒ Cascadeless ⇒ Recoverable.
Conflict serializable ⇒ View serializable.
