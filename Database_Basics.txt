# PART I — DATABASE FUNDAMENTALS AND DATA MODELING

# 1. DBMS FUNDAMENTALS & DATABASE ARCHITECTURE

## 1.1 Database

A **database** is an organized collection of logically related data that can be stored, accessed, managed, and updated efficiently.

### Example

A university database may contain:

* Student information
* Department information
* Course information
* Faculty information
* Enrollment records
* Examination records

---

## 1.2 Database Management System

A **Database Management System (DBMS)** is software that provides facilities for creating, storing, retrieving, updating, securing, and managing data in a database.

### Major Functions

1. Data storage and organization
2. Data retrieval
3. Data insertion, modification, and deletion
4. Security and authorization
5. Integrity constraint enforcement
6. Transaction management
7. Concurrency control
8. Backup and recovery
9. Query processing and optimization
10. Data independence

---

## 1.3 Advantages of DBMS

* Reduces unnecessary data redundancy
* Improves data consistency
* Supports controlled data sharing
* Provides security
* Enforces integrity constraints
* Supports concurrent access
* Provides transaction management
* Provides backup and recovery
* Provides data independence
* Simplifies database administration

---

## 1.4 Three-Level Database Architecture

The three-level architecture separates the user's view, logical database structure, and physical storage.

### External Level

The **external level** represents individual user or application views of the database.

Different users can have different views of the same database.

### Conceptual Level

The **conceptual level** represents the complete logical structure of the database.

It describes:

* Entities
* Relationships
* Attributes
* Constraints
* Logical database structure

### Internal Level

The **internal level** describes how data is physically stored.

It includes concepts such as:

* Files
* Pages
* Blocks
* Record layouts
* Indexes
* Storage structures

### Architecture

```text
Users / Applications
        ↓
External / View Level
        ↓
Conceptual / Logical Level
        ↓
Internal / Physical Level
        ↓
Physical Storage
```

---

## 1.5 Data Independence

Data independence means that changes at one level can be made without unnecessarily affecting higher levels.

### Physical Data Independence

Ability to change the **internal/physical schema** without changing the conceptual schema.

Examples:

* Changing file organization
* Adding or removing indexes
* Changing page organization
* Changing physical storage structures

### Logical Data Independence

Ability to change the **conceptual schema** without requiring changes to external views or application programs.

Examples:

* Adding attributes
* Adding relations
* Modifying logical relationships

### Comparison

| Type                       | Change Occurs At | Higher Level Protected |
| -------------------------- | ---------------- | ---------------------- |
| Physical Data Independence | Internal level   | Conceptual level       |
| Logical Data Independence  | Conceptual level | External level         |

---

## 1.6 Schema and Instance

### Schema

A **schema** describes the structure/design of the database.

Example:

```text
Student(RollNo, Name, Marks, DeptID)
```

Schema changes relatively infrequently.

### Instance

An **instance** is the actual data stored in the database at a particular point in time.

Example:

```text
101 | Rahul | 85 | 10
102 | Priya | 91 | 20
```

Instances change frequently.

---

## 1.7 Database Administrator

A **Database Administrator (DBA)** manages and maintains the database environment.

### Responsibilities

* User authorization
* Security management
* Backup and recovery
* Storage management
* Performance monitoring
* Integrity enforcement
* Access control
* Database maintenance
* Resource management

---

# 2. ENTITY-RELATIONSHIP MODEL

The ER model provides a conceptual way to design a database before implementing it using relational tables.

---

## 2.1 Entity

An **entity** is a distinguishable real-world object.

Examples:

* Student
* Employee
* Department
* Course

---

## 2.2 Entity Set

An **entity set** is a collection of similar entities.

Example:

```text
STUDENT
```

may contain all student entities.

---

## 2.3 Attributes

An attribute describes a property of an entity.

### Simple Attribute

Cannot be meaningfully divided further.

Example:

```text
Gender
```

### Composite Attribute

Can be divided into smaller components.

Example:

```text
Name
├── FirstName
├── MiddleName
└── LastName
```

### Single-Valued Attribute

Has one value for an entity.

### Multivalued Attribute

Can have multiple values.

Example:

```text
PhoneNumbers
```

### Stored Attribute

Directly stored in the database.

Example:

```text
DateOfBirth
```

### Derived Attribute

Calculated from another attribute.

Example:

```text
Age
```

derived from:

```text
DateOfBirth
```

### Key Attribute

Uniquely identifies an entity.

---

## 2.4 Relationship

A relationship represents an association between entity sets.

Example:

```text
STUDENT ─── ENROLLS ─── COURSE
```

---

## 2.5 Relationship Degree

### Unary Relationship

Involves one entity set.

```text
Employee manages Employee
```

### Binary Relationship

Involves two entity sets.

```text
Student enrolls in Course
```

### Ternary Relationship

Involves three entity sets.

---

## 2.6 Cardinality

Cardinality specifies how many entities can participate in a relationship.

### One-to-One

```text
1 : 1
```

### One-to-Many

```text
1 : N
```

### Many-to-One

```text
N : 1
```

### Many-to-Many

```text
M : N
```

---

## 2.7 Participation

### Total Participation

Every entity must participate in the relationship.

### Partial Participation

Participation is optional for some entities.

---

## 2.8 Weak Entity

A weak entity cannot be uniquely identified using its own attributes alone.

It depends on an owner/strong entity.

Characteristics:

* Does not have a complete key of its own
* Has a partial key
* Has total participation in its identifying relationship
* Traditionally represented using a double rectangle
* Identifying relationship traditionally represented using a double diamond

---

## 2.9 Relationship Attributes

Some attributes belong to the relationship rather than an individual entity.

Example:

```text
STUDENT ─── ENROLLS ─── COURSE
                  |
                Grade
```

`Grade` describes the enrollment relationship.

---

## 2.10 Specialization

Specialization is a top-down process in which a general entity is divided into specialized subclasses.

```text
Employee
   ├── Faculty
   └── Staff
```

---

## 2.11 Generalization

Generalization is a bottom-up process in which common properties of multiple entities are combined into a generalized entity.

---

## 2.12 Disjoint and Overlapping Constraints

### Disjoint

An entity can belong to at most one subclass.

### Overlapping

An entity may belong to multiple subclasses.

---

## 2.13 Total and Partial Specialization

### Total Specialization

Every superclass entity must belong to at least one subclass.

### Partial Specialization

Some superclass entities may belong to no subclass.

---

## 2.14 ER-to-Relational Mapping

### Strong Entity

Map the entity to a relation.

```text
EMPLOYEE(EmployeeID, Name, Salary)
```

### Composite Attribute

Store the component attributes.

```text
Name → FirstName, LastName
```

### Multivalued Attribute

Create a separate relation.

```text
EmployeePhone(EmployeeID, Phone)
```

### 1:N Relationship

Place the key of the 1-side as a foreign key in the N-side.

```text
DEPARTMENT(DeptID, DeptName)

EMPLOYEE(EmployeeID, Name, DeptID)
```

### M:N Relationship

Create a separate relation containing the keys of both participating entities and any relationship attributes.

```text
ENROLLMENT(StudentID, CourseID, Grade)
```

---

# PART II — RELATIONAL DATABASE MODEL

# 3. RELATIONAL MODEL, KEYS & INTEGRITY CONSTRAINTS

## 3.1 Relational Model

The relational model represents data using **relations**, commonly implemented as tables.

### Basic Terminology

| Relational Term | Meaning               |
| --------------- | --------------------- |
| Relation        | Table                 |
| Tuple           | Row                   |
| Attribute       | Column                |
| Domain          | Set of allowed values |
| Cardinality     | Number of tuples      |
| Degree          | Number of attributes  |

---

## 3.2 Keys

### Super Key

A **super key** is any set of attributes that uniquely identifies a tuple.

It may contain unnecessary attributes.

### Candidate Key

A **candidate key** is a minimal super key.

### Primary Key

A candidate key selected as the main identifier of tuples.

Properties:

* Uniquely identifies tuples
* Cannot contain NULL values
* A relation has one primary-key constraint
* Can be composite

### Alternate Key

A candidate key that is not selected as the primary key.

### Foreign Key

An attribute or set of attributes referencing an appropriate key in another relation.

### Composite Key

A key consisting of multiple attributes.

Example:

```text
Enrollment(StudentID, CourseID, Grade)
```

`(StudentID, CourseID)` may form a composite key.

---

## 3.3 SQL Example — Keys

```sql
CREATE TABLE Department (
    DeptID INT PRIMARY KEY,
    DeptName VARCHAR(50)
);

CREATE TABLE Student (
    RollNo INT PRIMARY KEY,
    Name VARCHAR(50),
    Marks INT,
    DeptID INT,
    FOREIGN KEY (DeptID)
        REFERENCES Department(DeptID)
);
```

---

## 3.4 Integrity Constraints

### Domain Integrity

Ensures that values belong to their permitted domain.

### Entity Integrity

A primary key cannot contain NULL.

### Referential Integrity

A foreign-key value must correspond to an appropriate referenced key value, subject to NULL and referential-action rules.

### Key Constraint

Ensures that key values uniquely identify tuples.

---

## 3.5 NULL

NULL represents an unknown, missing, or not-applicable value.

NULL is not:

* Zero
* Empty string
* False

Correct comparison:

```sql
SELECT *
FROM Student
WHERE Marks IS NULL;
```

Filters groups after grouping.


| WHERE                           | HAVING                                |
| ------------------------------- | ------------------------------------- |

## 4.16 Joins

### INNER JOIN

Returns matching rows.

```sql
SELECT S.Name, D.DeptName
FROM Student S
INNER JOIN Department D
ON S.DeptID = D.DeptID;
```

### LEFT JOIN

Returns all rows from the left relation and matching rows from the right relation.

### RIGHT JOIN

Returns all rows from the right relation and matching rows from the left relation.

### FULL OUTER JOIN

Returns rows from both relations, matching where possible.

### SELF JOIN

```sql
SELECT E.Name, M.Name AS Manager
FROM Employee E
JOIN Employee M
ON E.ManagerID = M.EmployeeID;
```

---

## 4.17 Join Multiplication

A one-to-many join can produce multiple output rows for a single row from one side.

When counting entities after such joins, use `COUNT(DISTINCT ...)` where appropriate.

```sql
SELECT COUNT(DISTINCT S.RollNo)
FROM Student S
JOIN Enrollment E
ON S.RollNo = E.StudentID;
```

---

## 4.18 Subqueries

### IN

Tests membership.

```sql
SELECT Name
FROM Student
WHERE DeptID IN (
    SELECT DeptID
    FROM Department
    WHERE DeptName = 'CSE'
);
```

### EXISTS

Checks whether at least one qualifying row exists.

```sql
SELECT S.Name
FROM Student S
WHERE EXISTS (
    SELECT 1
    FROM Enrollment E
    WHERE E.StudentID = S.RollNo
);
```

### ANY

The comparison must be true for at least one returned value.

### ALL

The comparison must be true for every returned value.

---

## 4.19 Correlated Subquery

A correlated subquery refers to a value from the outer query.

```sql
SELECT S.Name, S.Marks
FROM Student S
WHERE S.Marks >
(
    SELECT AVG(S2.Marks)
    FROM Student S2
    WHERE S2.DeptID = S.DeptID
);
```

---

## 4.20 NULL and Three-Valued Logic

SQL conditions can evaluate to:

```text
TRUE
FALSE
UNKNOWN
```

Examples:

```text
FALSE AND UNKNOWN = FALSE
TRUE OR UNKNOWN = TRUE
```

Use:

```sql
IS NULL
IS NOT NULL
```

rather than:

```sql
= NULL
```

For anti-match queries, `NOT EXISTS` can avoid the NULL-related behavior associated with `NOT IN`.

---

## 4.21 Set Operations

### UNION

Combines results and removes duplicates.

### UNION ALL

Combines results while retaining duplicates.

### INTERSECT

Returns common rows.

### EXCEPT

Returns rows from the first result that are absent from the second.

The participating result sets must have compatible structures.

---

## 4.23 DISTINCT

# 5. RELATIONAL ALGEBRA

Relational algebra is a procedural query language for the relational model.

It describes how a result can be obtained from relations.

---

## 5.1 Selection — σ

Selects rows satisfying a condition.

```text
σ Marks > 80 (Student)
```

SQL equivalent:

```sql
SELECT *
FROM Student
WHERE Marks > 80;
```

---

## 5.2 Projection — π

Selects required attributes.

```text
π Name, Marks (Student)
```

SQL equivalent:

```sql
SELECT Name, Marks
FROM Student;
```

Classical relational algebra treats relations as sets, so duplicate tuples are eliminated by projection.

---

## 5.3 Union — ∪

```text
R ∪ S
```

Requires union-compatible relations.

---

## 5.4 Difference — −

```text
R − S
```

Returns tuples present in `R` but not in `S`.

Difference is directional.

---

## 5.5 Cartesian Product — ×

```text
R × S
```

If:

```text
|R| = m
|S| = n
```

then:

```text
|R × S| = m × n
```

---

## 5.6 Rename — ρ

Used to rename relations or attributes.

It is particularly useful in self-joins.

---

## 5.7 Joins

### Theta Join

Uses an explicit comparison condition.

### Natural Join

Uses common attributes and removes duplicate copies of common join attributes.

---

## 5.8 Division

Division represents queries involving a **“for all”** requirement.

```text
R ÷ S
```

returns values from `R` associated with every required value represented by `S`.

---

## 5.9 SQL and Relational Algebra

| Relational Algebra | SQL                   |
| ------------------ | --------------------- |
| σ                  | WHERE                 |
| π                  | SELECT columns        |
| ∪                  | UNION                 |
| ∩                  | INTERSECT             |
| −                  | EXCEPT                |

# PART IV — FUNCTIONAL DEPENDENCIES AND DATABASE DESIGN

# 6. FUNCTIONAL DEPENDENCIES & ATTRIBUTE CLOSURE

## 6.1 Functional Dependency

A functional dependency is written as:

```text
X → Y
```

It means that if two tuples have the same value of `X`, they must have the same value of `Y`.

`X` is the determinant.

`Y` is functionally dependent on `X`.

---

## 6.2 Trivial Functional Dependency

```text
X → Y
```

is trivial when:

```text
Y ⊆ X
```

Example:

```text
AB → A
```

---

## 6.3 Non-Trivial Functional Dependency

A dependency is non-trivial when:

```text
Y ⊄ X
```

---

## 6.4 Completely Non-Trivial Functional Dependency

When:

```text
X ∩ Y = ∅
```

---

## 6.5 Armstrong's Axioms

### Reflexivity

If:

```text
Y ⊆ X
```

then:

```text
X → Y
```

### Augmentation

If:

```text
X → Y
```

then:

```text
XZ → YZ
```

### Transitivity

If:

```text
X → Y
Y → Z
```

then:

```text
X → Z
```

---

## 6.6 Derived Rules

### Union

```text
X → Y
X → Z
────────
X → YZ
```

### Decomposition

```text
X → YZ
────────
X → Y
X → Z
```

### Pseudotransitivity

```text
X → Y
WY → Z
────────
WX → Z
```

---

## 6.7 Attribute Closure

The closure of `X` is written:

```text
X+
```

It contains all attributes functionally determined by `X`.

### Example

Given:

```text
R(A, B, C, D, E)
```

and:

```text
A → B
B → C
CD → E
```

Find:

```text
AD+
```

Start:

```text
AD+ = {A, D}
```

From `A → B`:

```text
{A, B, D}
```

From `B → C`:

```text
{A, B, C, D}
```

From `CD → E`:

```text
{A, B, C, D, E}
```

Therefore:

```text
AD+ = {A, B, C, D, E}
```

Since all attributes are present, `AD` is a super key.

If it is minimal, it is a candidate key.

---

## 6.8 Candidate Key Identification

Procedure:

1. Identify attributes that do not occur on the RHS of any FD.
2. Such attributes generally need to be present in every candidate key.
3. Compute attribute closure.
4. If closure contains all attributes, the set is a super key.
5. Remove unnecessary attributes.
6. A minimal super key is a candidate key.

---

# 7. NORMALIZATION

## 7.1 Purpose

Normalization organizes relations to reduce:

* Redundancy
* Update anomalies
* Insertion anomalies
* Deletion anomalies

---

## 7.2 First Normal Form — 1NF

A relation is in 1NF when:

* Attribute values are atomic.
* Repeating groups are eliminated.
* Each cell contains a single logical value.

---

## 7.3 Second Normal Form — 2NF

A relation is in 2NF when:

1. It is in 1NF.
2. No non-prime attribute is partially dependent on a candidate key.

Partial dependency occurs when a non-prime attribute depends on only part of a composite candidate key.

If all candidate keys are single-attribute and the relation is in 1NF, it is automatically in 2NF.

---

## 7.4 Prime and Non-Prime Attributes

### Prime Attribute

Belongs to at least one candidate key.

### Non-Prime Attribute

Belongs to no candidate key.

---

## 7.5 Third Normal Form — 3NF

For every non-trivial functional dependency:

```text
X → A
```

at least one must hold:

1. `X` is a super key, or
2. `A` is a prime attribute.

---

## 7.6 Boyce-Codd Normal Form — BCNF

A relation is in BCNF if for every non-trivial FD:

```text
X → Y
```

`X` is a super key.

Therefore:

```text
BCNF ⇒ 3NF
```

but:

```text
3NF ⇏ BCNF
```

---

## 7.7 Example: 3NF but not BCNF

Consider:

```text
R(Student, Course, Instructor)
```

with:

```text
Course → Instructor
Instructor → Course
```

Candidate keys may include:

```text
(Student, Course)
(Student, Instructor)
```

`Course` and `Instructor` are prime attributes.

The relation can satisfy 3NF because the RHS attributes are prime.

However, `Course` and `Instructor` need not be super keys, so BCNF can fail.

---

## 7.8 Lossless Decomposition

A decomposition is lossless if joining the decomposed relations reconstructs the original relation without spurious tuples or loss of information.

For a binary decomposition into `R1` and `R2`, a standard condition is:

```text
(R1 ∩ R2) → R1
```

or:

```text
(R1 ∩ R2) → R2
```

under the relevant functional-dependency closure.

---

## 7.9 Dependency Preservation

A decomposition is dependency preserving if the original functional dependencies can be enforced using the decomposed relations without requiring joins.

Losslessness and dependency preservation are separate properties.

---

# PART V — TRANSACTION MANAGEMENT

# 8. TRANSACTIONS & SERIALIZABILITY

## 8.1 Transaction

A transaction is a logical unit of database work.

Example: transferring ₹500 from one account to another.

```text
T1:

Read(A)
A = A - 500
Write(A)

Read(B)
B = B + 500
Write(B)

COMMIT
```

---

## 8.2 ACID Properties

### Atomicity

All operations occur or the transaction is rolled back.

### Consistency

The transaction preserves defined database constraints and moves the database between valid states.

### Isolation

Concurrent transactions are controlled so that intermediate effects do not cause unacceptable interference.

### Durability

Committed effects survive appropriate failures according to the recovery mechanism.

---

## 8.3 Transaction States

```text
             Partially Committed
            /                   \
Active -----------------------> Committed
  |
  ↓
Failed
  |
  ↓
Aborted
  |
  ├── Restart
  └── Terminate
```

---

## 8.4 COMMIT

```sql
START TRANSACTION;

UPDATE Account
SET Balance = Balance - 500
WHERE AccountID = 101;

UPDATE Account
SET Balance = Balance + 500
WHERE AccountID = 102;

COMMIT;
```

`COMMIT` successfully completes the transaction and makes its effects durable according to the database's transaction/recovery protocol.

---

## 8.5 ROLLBACK

```sql
START TRANSACTION;

UPDATE Account
SET Balance = Balance - 500
WHERE AccountID = 101;

ROLLBACK;
```

`ROLLBACK` cancels uncommitted changes made by the transaction.

---

## 8.6 SAVEPOINT

```sql
START TRANSACTION;

UPDATE Account
SET Balance = Balance - 500
WHERE AccountID = 101;

SAVEPOINT P1;

UPDATE Account
SET Balance = Balance - 200
WHERE AccountID = 102;

ROLLBACK TO P1;

COMMIT;
```

A savepoint provides an intermediate rollback point within a transaction.

---

## 8.7 Schedule

A schedule represents the ordering/interleaving of operations from multiple transactions.

### Serial Schedule

Transactions execute completely one after another.

### Non-Serial Schedule

Operations from multiple transactions are interleaved.

A non-serial schedule can still be correct if it is serializable.

---

## 8.8 Conflicting Operations

Two operations conflict when:

1. They belong to different transactions.
2. They operate on the same data item.
3. At least one is a write.

| Operations  | Conflict |
| ----------- | -------- |
| Read-Read   | No       |
| Read-Write  | Yes      |
| Write-Read  | Yes      |
| Write-Write | Yes      |

---

## 8.9 Conflict Serializability

A schedule is conflict serializable if it is conflict-equivalent to a serial schedule.

### Precedence Graph

* Each transaction is a node.
* Add `Ti → Tj` when a conflicting operation of `Ti` precedes the corresponding conflicting operation of `Tj`.

```text
Acyclic graph → Conflict serializable
Cyclic graph  → Not conflict serializable
```

A topological ordering of an acyclic graph gives an equivalent serial order.

---

## 8.10 Recoverable Schedule

If `Tj` reads a value written by `Ti`, then `Ti` must commit before `Tj` commits.

---

## 8.11 Cascadeless Schedule

Transactions read only committed data.

This prevents cascading rollback caused by dirty reads.

---

## 8.12 Strict Schedule

If `Ti` writes an item, no other transaction may read or write that item until `Ti` commits or aborts.

Relationship:

```text
Strict
  ↓
Cascadeless
  ↓
Recoverable
```

---

## 8.13 View Serializability

View serializability considers:

* Initial reads
* Read-from relationships
* Final writes

Every conflict-serializable schedule is view-serializable, but some view-serializable schedules are not conflict-serializable.

---

# 9. CONCURRENCY CONTROL

## 9.1 Purpose

Concurrency control maintains correctness when multiple transactions execute concurrently.

---

## 9.2 Lost Update

One transaction's update is overwritten by another transaction.

---

## 9.3 Dirty Read

A transaction reads data written by another transaction before that transaction commits.

---

## 9.4 Unrepeatable Read

A transaction reads the same row twice and obtains different values because another transaction modified it between the reads.

---

## 9.5 Phantom Read

A repeated range query returns a different set of rows because another transaction inserted, deleted, or changed rows that satisfy the query condition.

---

## 9.6 Shared Lock

A shared lock `S` is used for reading.

Multiple transactions can hold compatible shared locks.

---

## 9.7 Exclusive Lock

An exclusive lock `X` is used for writing.

It conflicts with shared and exclusive locks held by other transactions.

### Compatibility

| Existing / Requested |   S |  X |
| -------------------- | --: | -: |
| S                    | Yes | No |
| X                    |  No | No |

---

## 9.8 Two-Phase Locking

2PL has two phases.

### Growing Phase

* Locks may be acquired.
* Locks are not released.

### Shrinking Phase

* Locks may be released.
* New locks are not acquired under standard 2PL.

2PL guarantees conflict serializability but can allow deadlocks.

---

## 9.9 Strict 2PL

Exclusive locks are held until commit or abort.

---

## 9.10 Rigorous 2PL

Both shared and exclusive locks are held until commit or abort.

```text
Rigorous 2PL
      ↓
 Strict 2PL
      ↓
      2PL
```

---

## 9.11 Deadlock

A deadlock occurs when transactions wait for one another in a cycle.

Example:

```text
T1 waits for T2
T2 waits for T1
```

---

## 9.12 Wait-For Graph

* Nodes represent transactions.
* `Ti → Tj` means `Ti` is waiting for `Tj`.

A cycle indicates deadlock.

---

## 9.13 Wait-Die

Using transaction age:

* Older requests resource held by younger → older waits.
* Younger requests resource held by older → younger aborts.

---

## 9.14 Wound-Wait

* Older requests resource held by younger → younger aborts.
* Younger requests resource held by older → younger waits.

---

## 9.15 Timestamp Ordering

Each transaction receives a timestamp.

Smaller timestamp generally means older transaction.

The system maintains values such as:

```text
ReadTS(X)
WriteTS(X)
```

Operations violating the required timestamp order may cause a transaction to abort or restart.

Timestamp ordering avoids lock-wait deadlocks.

---

# PART VI — STORAGE AND ACCESS METHODS

# 10. STORAGE & FILE ORGANIZATION

## 10.1 Storage Hierarchy

```text
CPU Registers
      ↓
Cache
      ↓
RAM
      ↓
SSD / Disk
```

Higher levels generally provide faster access with smaller capacity.

---

## 10.2 Pages and Blocks

DBMSs commonly transfer data between secondary storage and memory in units such as pages or blocks.

Database performance is therefore strongly influenced by the number of page/block transfers.

---

## 10.3 Record

A record is the storage representation of a tuple.

Example:

```text
101 | Rahul | 85 | CSE
```

---

## 10.4 Fixed-Length Records

All records have the same size.

Advantages:

* Simple storage management
* Easy address calculation
* Efficient access

---

## 10.5 Variable-Length Records

Records can have different sizes.

They may require:

* Length information
* Offset information
* Slot directories
* Additional metadata

---

## 10.6 Slotted Page

A slotted page is commonly used for variable-length records.

```text
+----------------------+
| Page Header          |
+----------------------+
| Record Data          |
| Record Data          |
|                      |
| Free Space           |
|                      |
+----------------------+
| Slot Directory       |
+----------------------+
```

The slot directory helps locate records within the page.

---

## 10.7 Spanned Records

A record may cross a page boundary.

```text
Page 1: [part of record]
Page 2: [remaining part]
```

---

## 10.8 Unspanned Records

A record must fit entirely inside a single page.

---

## 10.9 File Organization

### Heap File

Records are stored without a specified ordering.

Suitable for simple and frequent insertions.

### Sequential / Ordered File

Records are maintained in a specified order.

Useful for ordered and sequential access.

### Hash File

Records are organized using hashing.

Useful for equality-based access.

### Clustered Organization

Related records are stored physically close together to improve locality.

---

## 10.10 Buffer Manager

The buffer manager manages database pages between storage and main memory.

Responsibilities:

* Fetch pages
* Manage memory frames
* Track page usage
* Select pages for replacement
* Write modified pages back to storage

---

## 10.11 Buffer Hit

The requested page is already present in memory.

---

## 10.12 Buffer Miss

The requested page is not present in memory and must be fetched from storage.

---

## 10.13 Dirty Page

A dirty page is a page modified in memory whose latest contents have not yet been written to the corresponding stable-storage location.

---

## 10.14 Blocking Factor

For fixed-length records:

```text
bfr = floor(Block Size / Record Size)
```

### Example

```text
Block size = 1000 bytes
Record size = 120 bytes
```

Therefore:

```text
bfr = floor(1000 / 120)
    = 8 records/block
```

---

## 10.15 Number of Blocks

```text
Number of blocks = ceil(Number of records / bfr)
```

Example:

```text
Records = 950
bfr = 8

Blocks = ceil(950 / 8)
       = 119
```

---

# 11. INDEXING & HASHING

## 11.1 Index

An index is an auxiliary data structure that helps locate records efficiently.

It maps search-key values to associated record/page locations.

---

## 11.2 Dense Index

Contains an index entry for every search-key value or record according to the indexing scheme.

### Advantage

Fast lookup.

### Disadvantage

Requires more storage.

---

## 11.3 Sparse Index

Contains fewer index entries.

Sparse indexing generally requires appropriately ordered underlying data.

---

## 11.4 Primary Index

An index associated with the ordering/primary search key of the data file.

---

## 11.5 Secondary Index

An index built on a non-ordering attribute or another search key.

---

## 11.6 Multilevel Index

An index can itself be indexed.

This reduces the number of index levels/pages accessed during searching.

---

## 11.7 B-Tree and B+ Tree

B-tree family structures are balanced multiway search trees.

---

## 11.8 B+ Tree

A typical B+ tree contains:

* Internal nodes containing search keys and child pointers
* Leaf nodes containing search-key entries and record/page pointers
* Linked leaf nodes

### Advantages

* Balanced height
* Efficient search
* Efficient insertion
* Efficient deletion
* Efficient range queries
* Ordered traversal

---

## 11.9 B+ Tree Order

For a B+ tree of order `m`, a common convention is:

```text
Maximum children = m
Maximum keys in internal node = m − 1
```

Minimum occupancy depends on the specific convention and implementation.

---

## 11.10 B+ Tree Search

A search follows one path from the root to a leaf.

Approximate complexity:

```text
O(logₘ N)
```

where:

* `m` = branching factor
* `N` = number of indexed entries

---

## 11.11 B+ Tree Insertion

1. Locate the appropriate leaf.
2. Insert the key.
3. If overflow occurs, split the node.
4. Propagate separator information upward.
5. A root split may increase tree height.

---

## 11.12 B+ Tree Deletion

1. Locate and delete the key.
2. Check for underflow.
3. Redistribute from a sibling if possible.
4. Otherwise merge nodes.
5. Adjust parent separator information.
6. A root merge may reduce tree height.

---

## 11.13 Hashing

Hashing maps a search key to a bucket.

A simple hash function is:

```text
h(K) = K mod m
```

when specified.

Example:

```text
K = 17
m = 5

h(17) = 17 mod 5
      = 2
```

---

## 11.14 Collision

A collision occurs when different keys map to the same bucket.

Methods include:

* Chaining
* Overflow buckets
* Open addressing where applicable

---

## 11.15 B+ Tree vs Hash

| Property          | B+ Tree                  | Hash                    |
| ----------------- | ------------------------ | ----------------------- |
| Equality search   | Efficient                | Very efficient          |
| Range search      | Efficient                | Generally poor          |
| Ordered traversal | Supported                | Not naturally supported |
| Structure         | Balanced tree            | Hash buckets            |
| Typical use       | Range and ordered access | Equality lookup         |

---

# PART VII — QUERY PROCESSING

# 12. QUERY PROCESSING & OPTIMIZATION

## 12.1 Query Processing Flow

```text
SQL Query
    ↓
Parsing / Translation
    ↓
Logical Representation
    ↓
Query Optimization
    ↓
Physical Execution Plan
    ↓
Execution
    ↓
Result
```

---

## 12.2 Parsing and Translation

The DBMS checks:

* SQL syntax
* Table names
* Column names
* Data types
* Semantic validity
* Query structure

The query is then translated into an internal representation.

---

## 12.3 Query Optimization

The optimizer searches for an efficient execution strategy among semantically equivalent alternatives.

### Cost Factors

* Disk I/O
* CPU processing
* Memory usage
* Intermediate result size
* Network cost in distributed systems

---

## 12.4 Query Tree

Example:

```text
        π Name
           |
      σ Marks > 80
           |
        STUDENT
```

---

## 12.5 Selection Pushdown

Selection operations can often be moved closer to base relations.

Instead of:

```text
Join
 ↓
Select
```

the optimizer may use:

```text
Select
 ↓
Join
```

when logically valid.

This reduces the number of tuples processed by later operations.

---

## 12.6 Projection Pushdown

Unnecessary columns can be removed early when they are not required by later operations.

This reduces:

* Tuple width
* Intermediate storage
* Data movement

---

## 12.7 Join Algorithms

### Nested-Loop Join

For each tuple in one relation, tuples in the other relation are examined.

General but potentially expensive.

### Indexed Nested-Loop Join

Uses an index on the inner relation's join attribute.

### Sort-Merge Join

Sorts both relations on the join attribute and then merges them.

### Hash Join

Uses hashing to partition/build and probe matching tuples.

Particularly useful for equality joins.

---

## 12.8 Materialization

An intermediate result is completely computed and stored before the next operation consumes it.

### Advantage

Intermediate results can be reused.

### Disadvantage

Requires additional storage and I/O.

---

## 12.9 Pipelining

Tuples are passed directly from one operator to another without fully storing the intermediate result.

### Advantages

* Reduces temporary storage
* Can reduce I/O
* Allows earlier result production

---

# PART VIII — DATABASE RECOVERY

# 13. DATABASE RECOVERY

## 13.1 Purpose

Database recovery restores the database to a correct and consistent state after failures.

---

## 13.2 Types of Failures

### Transaction Failure

A transaction cannot complete successfully.

Examples:

* Constraint violation
* Logical error
* Explicit rollback

### System Failure

A crash or power failure causes loss of volatile state.

### Media Failure

Storage media becomes damaged or data becomes inaccessible.

---

## 13.3 Log-Based Recovery

A log records transaction activity.

Example:

```text
<T1 START>
<T1, A, old_value, new_value>
<T1 COMMIT>
```

The exact format depends on the recovery system.

---

## 13.4 Write-Ahead Logging

The write-ahead logging principle requires the necessary log record to reach stable storage before the corresponding modified database page is written to stable storage.

This ensures that recovery information is available before the affected database page is persisted.

---

## 13.5 UNDO

UNDO restores the previous value.

Example:

```text
Old value = 500
New value = 300
```

UNDO restores:

```text
500
```

---

## 13.6 REDO

REDO reapplies a committed change.

Example:

```text
Old value = 500
New value = 300
```

REDO ensures that:

```text
300
```

is reflected after recovery.

---

## 13.7 Deferred Update

Under the basic deferred-update model, database changes are delayed until transaction commit.

Recovery generally requires REDO for committed transactions because uncommitted changes have not been applied to the database.

---

## 13.8 Immediate Update

Database changes may be written before transaction commit.

Recovery may therefore require:

```text
UNDO + REDO
```

depending on the recovery protocol.

---

## 13.9 Checkpoint

A checkpoint establishes a recovery point and reduces the amount of log that normally needs to be examined during recovery.

A checkpoint reduces recovery work but does not eliminate recovery.

---

## 13.10 Cascading Rollback

A cascading rollback occurs when a transaction must be rolled back because it depended on data written by another transaction that subsequently failed.

Preventing transactions from reading uncommitted data avoids this problem.

---

## 13.11 Shadow Paging

Shadow paging maintains:

* A shadow page table
* A current page table

The shadow structure preserves a stable reference to the previous database state while changes are made through the current structure.

---
