1.4 PAGE_SIZE

`PAGE_SIZE` defines the size of one database page.

MyRDB uses:

```text
4096 bytes = 4 KB
```

fixed-size pages.

Database files are divided into these pages.

Example

```text
Database File
│
├── Page 0 → 4096 bytes
├── Page 1 → 4096 bytes
├── Page 2 → 4096 bytes
└── Page 3 → 4096 bytes
```

Each page has the same fixed size.

Why fixed-size pages?

Fixed-size pages make:

1. Disk storage easier to manage.
2. Page addressing predictable.
3. Page offsets easy to calculate.
4. Page-level reading and writing easier.

The storage engine can calculate a page's location using:

```text
Page Offset = Page ID × PAGE_SIZE
```

For example:

```text

PAGE_SIZE = 4096

Page Offset = 2 × 4096
            = 8192 bytes
```

The Page Header contains five fields.

2.7 Byte Order / Endianness

New Concept

Endianness means the order in which multiple bytes of a value are stored.

When MyRDB converts values such as:

1. Page ID
2. Version
3. Record Count
4. Free Space

into bytes, the byte order must be defined.

There are two common byte orders.
-------------
Little-Endian

The least significant byte is stored first.

Example:

```text
Number = 0x12345678
```

Little-Endian representation:

```text
78 56 34 12
```
-------------
Big-Endian

The most significant byte is stored first.

Big-Endian representation:

```text
12 34 56 78
```
-------------
Why Does MyRDB Need Endianness?

MyRDB stores pages as binary data.

Therefore, the database format must define how multi-byte numbers are represented.

A fixed byte order ensures predictable interpretation of the binary format.

MyRDB Choice

MyRDB uses:

```text
Little-Endian
```

Therefore, the struct format becomes:

The `<` specifies Little-Endian.

3.4 Slot Directory

A Slot Directory stores the location information needed to find records inside a page. Each slot entry maps a page-local Slot ID to a record's offset and length.

Example

```text
Slot 0 → Offset 100, Length 20
Slot 1 → Offset 120, Length 25
Slot 2 → Offset 145, Length 18
```

Records can have different serialized sizes, so the engine needs their exact starting positions and lengths rather than assuming every record occupies the same amount of space.

A slot entry contains or represents:
- Slot ID: identifies the entry within the page.
- Offset: the starting byte position of the record inside the page.
- Length: the number of bytes occupied by the record.

If Slot 1 stores offset 120 and length 25, the record begins at byte 120 and occupies 25 bytes. The engine uses the slot entry to read those bytes and then deserialize them into a logical record.

Record-location flow: Page ID → Slot ID → Slot entry → Offset and Length → Record Bytes → Deserialization → Logical Record.

The Slot Directory is separate from the record data itself: it tells the engine where the bytes are, not what the record's field values mean.

3.5 Slot ID

A Slot ID identifies a record's slot within a particular page. It is an internal storage identifier, not the record's Primary Key.

Example: Student ID 101 may be stored in Slot 0. The user-facing ID identifies the logical row, while the Slot ID helps the storage engine locate its slot entry.

Slot IDs are page-local. Page 0, Slot 1 and Page 1, Slot 1 may refer to different records. A physical reference therefore needs both Page ID and Slot ID.

Slot Behavior During DELETE

Before deletion, slots might refer to Records A, B, and C at Slot IDs 0, 1, and 2. After deleting B, Slot 1 is marked deleted or free while Slot 2 remains in place. The engine does not automatically shift C into Slot 1, because shifting slots could change existing internal references. A deleted slot may be reused later if the implementation safely supports reuse.

Key relationship: Page ID → Slot ID → Slot Entry → Offset and Length → Record Bytes.

A Slot ID identifies the page-local slot; its slot entry supplies the physical location details.

3.6 Record Offset & Length

Offset is the starting byte position of a record inside its page. Length is the number of bytes occupied by that record.

Example: Offset 100 and Length 20 means start at byte 100 and read 20 bytes, covering byte positions 100–119.

Page Offset vs Record Offset

- Page Offset: where the page starts in the database file.
- Record Offset: where the record starts inside the page.
- Length: how many record bytes to read.

For a 4096-byte page, Page 5 starts at 5 × 4096 = 20480 bytes. If the record offset is 100, its absolute file position is 20480 + 100 = 20580 bytes.

The physical location flow is Page ID → page offset in file → Slot ID → slot entry → record offset and length → record bytes. Offset answers “where do I start?”; length answers “how many bytes do I read?”

Free Space is the unused space available inside a page for storing records.

```text

```


3.8 Record Insert

Record Insert stores a new logical record inside a page. A future SQL INSERT request must be parsed and converted into a record before physical storage.

Insert Flow

```text
INSERT Request
   ↓
Logical Record
   ↓
Serialize to Bytes
   ↓
Find a Suitable Page
   ↓
Store Record Bytes
   ↓
Create Slot Entry
   ↓
Update Page Metadata
```

The engine checks whether the page has enough free space for the serialized record, slot entry, and applicable overhead. For example, a 15-byte record with an 8-byte slot entry needs at least 23 bytes of usable space. If the record begins at offset 100 and occupies 11 bytes, its slot entry records offset 100 and length 11.

If the current page cannot fit the record, the storage system must look for another suitable page or allocate a new one. Chapter 4 develops this multi-page coordination. Page metadata must reflect the insert, including the active record count, slot information, and free space.

The current record encoding is a simple learning format and is not yet a robust general-purpose binary record format.

```text
Deserialize
       ↓
Return Logical Record
```

For example, if a slot contains offset 100 and length 15, the engine reads 15 bytes starting at byte 100. In a byte array, the same range is selected from offset through offset + length, excluding the ending index.

Deserialization reverses the record serialization process. INSERT converts a logical record into bytes for storage; READ retrieves those bytes and converts them back into a logical record. The slot directory provides the location, while the record format determines how the bytes are interpreted.

3.10 Record Update

Record Update modifies an existing stored record. A request such as changing a student's age requires the engine to locate the row, read it, modify its values, serialize the updated record, and store the result.

Update Flow

```text
Find Record
   ↓
Read and Modify Values
   ↓
Serialize Updated Record
   ↓
Check Available Space
   ↓
Write Updated Record
   ↓
Update Slot and Metadata
```

Updates are more complicated than reads because the serialized size may change. If the new record fits in the existing allocation, it may be updated in place. If it is larger and cannot fit, the engine must find suitable space, store the new bytes, and update the slot entry to the new offset and length. The slot ID can continue identifying the same slot while its location information changes.

An UPDATE therefore does not guarantee that the same physical bytes are overwritten. The safe approach depends on record size, free space, and the storage design.

3.11 Record Delete

Record Delete makes an existing record inactive and allows its storage to become reusable. The engine locates the record through its page and slot, marks it deleted, updates the slot state and page metadata, and maintains free-space information.

Delete Flow

```text
Locate Record
   ↓
Find Slot and Record Location
   ↓
Mark Record Deleted
   ↓
Mark Space Reusable
   ↓
Update Slot and Page Metadata
```

Slot Behavior

If Slots 0, 1, and 2 refer to Records A, B, and C, deleting B generally marks Slot 1 deleted or free without moving C from Slot 2. Stable slot positions help preserve internal references. A later insert may reuse a deleted slot if the implementation supports it safely.

Logical Deletion vs Physical Erasure

Logical deletion means the record is no longer active or visible. Physical erasure means overwriting or removing the bytes themselves. These are different operations: a deleted record's old bytes do not necessarily need to be erased immediately, provided the engine no longer treats them as an active record.

Free-space accounting is not always as simple as adding the deleted record's length. Slot-directory space, fragmentation, and record layout also affect reusable space. MyRDB must keep record state, slot state, and page metadata consistent.

4.1 Storage Engine Objective

A Storage Engine coordinates how database data is stored, accessed, modified, and maintained in physical storage. It connects page-level and record-level operations into a broader storage system.

Why MyRDB Needs It

Chapter 2 established page creation, reading, writing, and validation. Chapter 3 added record insertion, reading, updating, and deletion within a page. When records span many pages, a higher-level component must choose pages, coordinate operations, and work with database files.

Planned Conceptual Flow

```text
Database Operation
      ↓
Storage Engine
      ↓
Page Management
      ↓
Page and Record Operations
      ↓
Database File on Disk
```

Responsibilities

1. Coordinate page and record operations across storage.
2. Work with the page-management layer to select or allocate pages.
3. Coordinate access to database files.
4. Provide a foundation for later persistence, indexing, and recovery integration.

Component Differences

- Page: physical storage unit containing metadata and stored data.
- Record management: performs record-level operations within a page.
- Page Manager: locates, tracks, and allocates pages.
- Storage Engine: coordinates broader storage operations across these components.

MyRDB Connection

The existing configuration defines 4096-byte pages, and the page engine provides the lower-level foundation. The full Storage Engine is a target design and is not yet implemented.

-------------
4.2 Multiple Page Management

Multiple Page Management means tracking and coordinating the pages belonging to a database file. A single 4096-byte page cannot hold unlimited records, so the engine must find a suitable page for each insert.

Why It Is Needed

For every new record, MyRDB needs to determine which pages belong to the database, whether an existing page has enough free space, and whether a new page must be allocated. Required space includes serialized record bytes, the slot-directory entry, and any other applicable overhead.

Example

| Page ID | Free space | Required space | Suitable? |
|---:|---:|---:|---|
| 0 | 100 bytes | 200 bytes | No |
| 1 | 500 bytes | 200 bytes | Yes |
| 2 | 250 bytes | 200 bytes | Yes |

If pages are checked in order, Page 1 is selected because it is the first page with sufficient space. If no existing page fits, the system must find or allocate another page.

Planned Flow

```text
Insert Record
      ↓
Check Existing Pages
      ↓
Enough Space?
  ┌───┴───┐
 Yes      No
  ↓        ↓
Use Page  Allocate New Page
      ↓
Store Record and Update Metadata
```

Page Location

Page size is fixed at 4096 bytes, so a page's starting file position is Page ID × 4096. Thus, Page 0 starts at byte 0, Page 1 at 4096, Page 2 at 8192, and Page 3 at 12288. If a record starts at offset 100 inside Page 2, its absolute file position is 8192 + 100 = 8292 bytes.

The page offset identifies where the page begins in the database file; the record offset identifies where a record begins inside that page. The full multi-page coordination and persistent page tracking are planned, not yet implemented.

-------------
4.3 Page Allocation and the Page Manager

Page allocation assigns a page-sized region of database storage so that data can be stored in it. MyRDB uses fixed-size pages of 4096 bytes. If no existing page has enough usable space for a record and its slot entry, the system may need to allocate another page. This does not mean reserving 4096 bytes of RAM permanently; memory buffers may be used temporarily while reading or writing a page.

Page Manager Responsibilities

1. Track pages belonging to a database file.
2. Find an existing page with enough free space.
3. Assign an ID to a newly allocated page.
4. Initialize a new page with a valid header and metadata.
5. Coordinate page reads and writes.
6. Help maintain consistent page metadata.

These responsibilities describe the planned design; the complete Page Manager is not implemented yet.

Allocation Flow

```text
Insert Request
      ↓
Check Existing Pages
      ↓
Suitable Page Found?
   ┌──┴──┐
  Yes    No
   ↓      ↓
Use Page  Allocate New Page
             ↓
        Initialize Page
             ↓
        Store Record
        Update Metadata
```

New Page Initialization — Planned Steps

1. Determine the next available page ID using a reliable strategy.
2. Calculate the page's position in the database file.
3. Initialize a 4096-byte page buffer.
4. Create a valid page header with the page ID and appropriate metadata.
5. Write the initialized page to the database file.
6. Make the page available for record operations.

Page ID Assignment

For a simple file with sequential IDs, the next ID may equal the existing page count; for example, IDs 0, 1, and 2 would be followed by 3. This is only a basic strategy. If pages can be deleted, reused, or allocated concurrently, counting pages may not identify a safe available ID. A robust allocator must track page usage reliably.

Page ID and File Position

The page ID identifies a page logically. Its starting file position is Page ID × 4096. Page 2 therefore starts at byte 8192; a record at offset 100 within it starts at absolute byte 8292.

Teaching Example and Limitations

A simple simulation can track each page ID and its available space, select the first suitable page, or assign a new ID when no page fits. Such a simulation only changes in-memory data: it does not create a real page, write a valid header, save the page to disk, or provide persistent page tracking. A simple maximum-ID-plus-one strategy also does not handle all deletion, reuse, or concurrency cases.

Persistence Requirement

When a database file is reopened, MyRDB must be able to discover existing pages and reconstruct the metadata needed to manage them. Persistent page tracking and disk-backed allocation have not yet been implemented or tested. Page allocation alone also does not provide transaction safety, crash recovery, or safe concurrent allocation; those require separate mechanisms.


Page Selection vs Page Allocation

- Page selection means choosing an already existing page that has sufficient usable space.
- Page allocation means assigning a new page when existing pages cannot satisfy the request.
- Page initialization prepares the new page's fixed-size buffer and header so it follows MyRDB's storage format.
- Page persistence means writing the page to the database file and being able to recognize it after reopening the database.

These are related but separate steps. A system can simulate page selection in memory without actually allocating or persisting a page. A complete implementation must coordinate all steps and handle failures without leaving the database's page metadata inconsistent.

Page Allocation Design Considerations

1. Page IDs must be unique within the relevant database file and must not accidentally point to an already used page.
2. A page must have the expected size, magic value, format version, and page ID in its header.
3. Free-space calculations must account for the page header, record bytes, slot entries, and the current layout.
4. The system must distinguish an unused page from a page that exists but has no room for the requested record.
5. After writing a page, the engine must maintain enough information to find that page during later reads and after a restart.
6. If multiple operations can allocate pages at the same time, allocation must be coordinated to avoid assigning the same page ID twice.

These are design requirements to verify during implementation, not features already proven by the current tests.

4.4 Database files & Persistent page Storage
1. Database File
A database file (.db) stores database pages on a storage device. Multiple fixed-size pages can be stored in a single file.

Example: college.db
2. Persistent Page Storage
Persistent storage means saving page data to non-volatile storage so that it remains available after the application closes or the system restarts.
- MyRDB page size: 4096 bytes (4 KB).
- Each page contains a header, slot-directory information, and record data.
- Page offset = Page ID × PAGE_SIZE.
3. Writing Pages to a File
The basic process is:
Create Page in Memory
        ↓
Serialize Data into Bytes
        ↓
Write Page to .db File
        ↓
Data Stored on Disk


- wb: Opens a file for writing and truncates existing contents.
- r+b: Reads and writes an existing file without truncating it.
4. Crash and Power Failure
- Data safely persisted to storage normally survives a crash.
- Data present only in RAM may be lost.
- A crash during writing may leave incomplete or corrupted data.
- file.flush() sends buffered data to the operating system.
- os.fsync() requests synchronization of file data and metadata to storage.
5. WAL and Crash Recovery
Write-Ahead Logging (WAL) records changes before corresponding database pages are written, enabling recovery after interrupted operations.
Write WAL → Persist Log → Update Page → Recover After Crash


MyRDB Implementation Status
Page-level reading and writing exist from earlier chapters. However, complete page-metadata reconstruction, WAL, and crash recovery still require implementation and testing.

Key difference: The database file stores pages; persistent storage preserves saved data; WAL helps recover a consistent state after a crash.
