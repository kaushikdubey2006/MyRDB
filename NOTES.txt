## 1.4 PAGE_SIZE

```python
PAGE_SIZE = 4096
```

`PAGE_SIZE` defines the size of one database page.

MyRDB uses:

```text
4096 bytes = 4 KB
```

fixed-size pages.

Database files are divided into these pages.

### Example

```text
Database File
│
├── Page 0 → 4096 bytes
├── Page 1 → 4096 bytes
├── Page 2 → 4096 bytes
└── Page 3 → 4096 bytes
```

Each page has the same fixed size.

### Why fixed-size pages?

Fixed-size pages make:

* Disk storage easier to manage.
* Page addressing predictable.
* Page offsets easy to calculate.
* Page-level reading and writing easier.

The storage engine can calculate a page's location using:

```text
Page Offset = Page ID × PAGE_SIZE
```

For example:

```text
Page ID = 2
PAGE_SIZE = 4096

Page Offset = 2 × 4096
            = 8192 bytes
```


### Why WAL?

WAL is mainly associated with:

* Crash recovery
* Durability
* Recovery after unexpected shutdown


The WAL location is configured in Chapter 1, while the actual WAL mechanism belongs to the recovery/transaction system.

# 2.4 Binary Data & struct

Database pages are ultimately stored as binary data.

A file does not directly store a Python object such as:

```python
{
    "page_id": 5,
    "record_count": 3
}
```

Instead, the values must be converted into bytes.

Python provides the `struct` module for this purpose.

### Packing

```text
Python Values
     ↓
struct.pack()
     ↓
Bytes
```

### Unpacking

```text
Bytes
  ↓
struct.unpack()
  ↓
Python Values
```

### MyRDB Storage Flow

```text
Page Header
     ↓
struct.pack()
     ↓
Binary Bytes
     ↓
Database File
```

When reading:

```text
Database File
     ↓
Binary Bytes
     ↓
struct.unpack()
     ↓
Page Header Values
```

### Important

`struct` performs conversion.

It does not itself write data to the database file.

File operations such as:

```python
read()
write()
seek()
```

perform the actual file I/O.

---

# 2.5 Page Header Binary Layout

The Page Header contains five fields.

| Field        |    Size | Purpose                           |
| ------------ | ------: | --------------------------------- |
| Magic        | 4 bytes | Identifies a valid MyRDB page     |
| Version      | 2 bytes | Identifies storage format version |
| Page ID      | 4 bytes | Identifies the page               |
| Record Count | 2 bytes | Number of records                 |
| Free Space   | 4 bytes | Available space                   |

### Total Header Size

```text
4 + 2 + 4 + 2 + 4
=
16 bytes
```

Therefore:

```text
PAGE_HEADER_SIZE = 16 bytes
```

### Binary Layout

```text
Byte 0–3
    ↓
Magic

Byte 4–5
    ↓
Version

Byte 6–9
    ↓
Page ID

Byte 10–11
    ↓
Record Count

Byte 12–15
    ↓
Free Space
```

### Remaining Page Space

Since the page is 4096 bytes:

```text
4096 - 16 = 4080 bytes
```

These remaining bytes are available for the rest of the page layout.

---

# 2.6 Field Sizes & Struct Format

Python's `struct` module uses format codes to describe binary fields.

### Struct Format Codes

| Code | Meaning                |    Size |
| ---- | ---------------------- | ------: |
| `4s` | 4-byte bytes field     | 4 bytes |
| `H`  | Unsigned short integer | 2 bytes |
| `I`  | Unsigned integer       | 4 bytes |

Therefore, the Page Header can be represented as:

```text
4s H I H I
```

Combined:

```text
"<4sHIHI"
```

### Meaning

```text
4s → Magic
H  → Version
I  → Page ID
H  → Record Count
I  → Free Space
```

### Example

```python
struct.pack(
    "<4sHIHI",
    b"MYDB",
    1,
    5,
    3,
    2000
)
```

The values represent:

```text
Magic        = MYDB
Version      = 1
Page ID      = 5
Record Count = 3
Free Space   = 2000
```

These values are converted into a fixed binary representation.

### Important

```text
struct.pack()
Python values → bytes
```

and:

```text
struct.unpack()
bytes → Python values
```

Again:

```text
struct → conversion
File I/O → actual file access
```

# 2.7 Byte Order / Endianness

## New Concept

Endianness means the order in which multiple bytes of a value are stored.

When MyRDB converts values such as:

* Page ID
* Version
* Record Count
* Free Space

into bytes, the byte order must be defined.

There are two common byte orders.

---

## Little-Endian

The least significant byte is stored first.

Example:

```text
Number = 0x12345678
```

Little-Endian representation:

```text
78 56 34 12
```

---

## Big-Endian

The most significant byte is stored first.

```text
Number = 0x12345678
```

Big-Endian representation:

```text
12 34 56 78
```

---

## Why Does MyRDB Need Endianness?

MyRDB stores pages as binary data.

Therefore, the database format must define how multi-byte numbers are represented.

A fixed byte order ensures predictable interpretation of the binary format.

### MyRDB Choice

MyRDB uses:

```text
Little-Endian
```

Therefore, the struct format becomes:

```python
"<4sHIHI"
```

The `<` specifies Little-Endian.

# 3.1 Record Storage Objective

## What is a Record?

A record is a complete set of related data representing one row of a table.

Example:

```text
Students
--------------------------------
ID      Name       Age
101     Aman       20
```

The following:

```text
101, Aman, 20
```

is one record.

---

## Why Is Record Storage Needed?

Chapter 2 focused on pages.

However, a page itself is not a database row.

A page is a physical storage unit.

Chapter 3 introduces the mechanism required to store actual database records inside those pages.

### Record vs Page

| Record                   | Page                               |
| ------------------------ | ---------------------------------- |
| Represents a logical row | Represents a physical storage unit |
| Contains field values    | Contains records and metadata      |
| Example: `101, Aman, 20` | Example: 4096-byte page            |
| Logical concept          | Physical storage concept           |

---

## Record Identification

A record will be physically referenced using:

```text
Page ID + Slot ID
```

The Slot Directory maps the Slot ID to the physical location of the record.

### MyRDB Flow

```text
SQL / Table Fields
      ↓
Logical Record
      ↓
Record Storage
      ↓
Page
```

### Small Example

```python
record = {
    "id": 101,
    "name": "Aman",
    "age": 20
}

print(record)
```

This represents a logical record.

It is not yet physically stored inside a page.

---

# 3.2 Record Structure

## What is Record Structure?

Record Structure defines how the fields of a record are organized and represented.

Example:

```text
Student Record
├── ID
├── Name
└── Age
```

For:

```text
101, Aman, 20
```

the fields are:

```text
ID   → 101
Name → Aman
Age  → 20
```

---

## Why Is Record Structure Needed?

MyRDB needs to know:

* Which fields belong to the record.
* What value each field contains.
* What data type each field has.
* How the record should be serialized.
* How the record should be reconstructed after reading.

---

## Record Structure vs Record Storage

These are different concepts.

### Record Structure

```text
ID = 101
Name = Aman
Age = 20
```

This describes the content of the record.

### Record Storage

```text
Page ID = 0
Slot ID = 1
Offset = 120
Length = 15
```

This describes where the record is physically stored.

Therefore:

```text
Record Structure
→ What the record contains

Record Storage
→ How and where it is stored
```

### MyRDB Flow

```text
Table Definition
      ↓
Record Structure
      ↓
Record Values
      ↓
Serialization
      ↓
Physical Storage
```

### Small Example

```python
record = {
    "id": 101,
    "name": "Aman",
    "age": 20
}

print(record["name"])
```

Output:

```text
Aman
```

# 3.3 Record Serialization

## What is Serialization?

Serialization is the process of converting a logical record into a byte representation that can be stored on disk.

### Basic Flow

```text
Logical Record
      ↓
Serialization
      ↓
Bytes
      ↓
Page / Disk
```

---

## Why Is Serialization Needed?

A database file stores binary data.

A Python dictionary such as:

```python
{
    "id": 101,
    "name": "Aman",
    "age": 20
}
```

cannot simply be written to the binary page in its Python-object form.

Therefore, MyRDB converts the record into bytes.

---

## Simple Example

```python
record = "101,Aman,20"

data = record.encode("utf-8")

print(data)
```

Output:

```text
b'101,Aman,20'
```

The string has been converted into bytes.

---

## Deserialization

The reverse process is called deserialization.

```text
Bytes
  ↓
Deserialization
  ↓
Logical Record
```

Example:

```python
data = b"101,Aman,20"

record = data.decode("utf-8")

print(record)
```

Output:

```text
101,Aman,20
```

---

## Chapter 2 Connection

### Chapter 2

```text
      ↓

```

### Chapter 3

```text
      ↓
```

# 3.4 Slot Directory

## What is a Slot Directory?

A Slot Directory is a structure inside a page that stores the physical location information of records.

The core relationship is:

```text
Slot ID → Offset + Length
```

### Example

```text
Slot 0 → Offset 100, Length 20
Slot 1 → Offset 120, Length 25
Slot 2 → Offset 145, Length 18
```

---

## Why Is Slot Directory Needed?

Records may have different sizes.

For example:

```text
101, Aman, 20
102, Rahul, 21
103, Christopher, 22
```

The serialized records may occupy different numbers of bytes.

Therefore, MyRDB needs a structure that tells it exactly where every record is located.

---

## Page Layout

```text
┌──────────────────────────────┐
│         PAGE HEADER          │
├──────────────────────────────┤
│                              │
│       RECORD STORAGE         │
│                              │
│        Record 1              │
│        Record 2              │
│        Record 3              │
│                              │
│        FREE SPACE            │
│                              │
├──────────────────────────────┤
│       SLOT DIRECTORY         │
│                              │
│ Slot 0 → Offset + Length     │
│ Slot 1 → Offset + Length     │
│ Slot 2 → Offset + Length     │
└──────────────────────────────┘
```

---

## Slot Entry

A slot entry contains location information such as:

```text
Slot ID
Offset
Length
```

Example:

```text
Slot ID = 1
Offset  = 120
Length  = 25
```

This means:

```text
The record starts at byte 120
and occupies 25 bytes.
```

---

## Offset

Offset is the starting byte position of the record inside the page.

Example:

```text
Offset = 100
```

means the record starts at byte 100.

---

## Length

Length is the number of bytes occupied by the record.

Example:

```text
Length = 20
```

means read 20 bytes.

Therefore:

```text
Offset tells WHERE to start.

Length tells HOW MANY bytes to read.
```

---

## Small Example

```python
slot_directory = [
    {"offset": 100, "length": 20},
    {"offset": 120, "length": 25},
    {"offset": 145, "length": 18}
]

print(slot_directory[1])
```

Output:

```text
{'offset': 120, 'length': 25}
```

Here:

```text
Slot ID = 1
Offset  = 120
Length  = 25
```

---

## Complete Record Location Flow

```text
Page ID
   ↓
Slot ID
   ↓
Offset + Length
   ↓
Record Bytes
   ↓
Deserialization
   ↓
Logical Record
```

### Key Relationship

```text
Page ID → Slot ID → Offset + Length → Record
```

This relationship is used throughout record operations.

---

# 3.5 Slot ID

## What is Slot ID?

Slot ID is an internal identifier used to identify a record's slot within a page.

Example:

```text
Slot 0 → Record A
Slot 1 → Record B
Slot 2 → Record C
```

A Slot ID points to the corresponding slot entry in the Slot Directory.

---

## Slot ID vs Primary Key

Slot ID and Primary Key are different.

### Primary Key

Identifies a logical database record.

### Slot ID

Identifies the physical storage entry of that record within a page.

Example:

```text
Student ID = 101
Slot ID    = 0
```

The user understands the Student ID.

The storage engine uses the Slot ID.

---

## Slot IDs Are Page-Local

A Slot ID only has meaning within its page.

For example:

```text
Page 0 + Slot 1
```

and:

```text
Page 1 + Slot 1
```

can refer to different records.

Therefore, the complete physical reference is:

```text
Page ID + Slot ID
```

---

## Slot Behavior During DELETE

Before deletion:

```text
Slot 0 → A
Slot 1 → B
Slot 2 → C
```

After deleting B:

```text
Slot 0 → A
Slot 1 → Deleted / Free
Slot 2 → C
```

We do not automatically shift C into Slot 1.

Keeping slot identity stable helps avoid changing existing internal references.

A deleted slot can potentially be reused later.

---

## Most Important Flow

```text
Page ID
   ↓
Slot ID
   ↓
Slot Entry
   ↓
Offset + Length
   ↓
Record Bytes
```

### One-Line Definition

> Slot ID identifies a record's slot within a page, while the slot entry provides the offset and length needed to locate that record's bytes.

---

# 3.6 Record Offset & Length

## Record Offset

Offset is the starting byte position of a record inside a page.

Example:

```text
Offset = 100
```

means the record starts at byte 100.

---

## Record Length

Length is the total number of bytes occupied by the record.

Example:

```text
Length = 20
```

means MyRDB should read 20 bytes.

---

## Example

```text
Slot 1 → Offset = 100, Length = 20
```

This means:

```text
Start = 100
Read  = 20 bytes
Range = 100–119
```

---

## Important Difference

### Page Offset

Tells where a page starts in the `.db` file.

```text
Page Offset = Page ID × PAGE_SIZE
```

### Record Offset

Tells where a record starts inside that page.

Therefore:

```text
Page Offset
     +
Record Offset
     =
Actual File Position
```

### Example

```text
Page ID = 5
PAGE_SIZE = 4096

Page Offset
= 5 × 4096
= 20480

Record Offset
= 100

Actual File Position
= 20480 + 100
= 20580
```

---

## Main Flow

```text
Page ID
   ↓
Slot ID
   ↓
Offset + Length
   ↓
Record Bytes
```

### Easy Memory Trick

```text
Offset → WHERE to start

Length → HOW MANY bytes to read
```

---

# 3.7 Free Space Management

Free Space is the unused space available inside a page for storing records.

MyRDB must check free space before inserting or updating a record.

---

## Required Space

Required space includes:

```text
Record Size
+
Slot Entry Size
```

Therefore:

```text
Required Space
=
Record Size + Slot Entry Size
```

---

## Example

Suppose:

```text
Free Space = 500 bytes
Record     = 100 bytes
Slot Entry = 8 bytes
```

Then:

```text
Required = 100 + 8
         = 108 bytes
```

Since:

```text
500 ≥ 108
```

the record fits.

---

## If Space Is Insufficient

Suppose:

```text
Free Space = 10 bytes
Required   = 23 bytes
```

The record does not fit.

The storage system can then look for another page.

```text
Page 0
   ↓
Not enough space
   ↓
Find/Create another page
```

---

## Free Space Changes

### INSERT

```text
Free Space decreases
```

### DELETE

```text
Free Space can become reusable
```

### UPDATE

Free space may:

* Increase
* Decrease
* Remain approximately similar

depending on the new serialized record size.

---

## Main Flow

```text
INSERT
   ↓
Check Free Space
   ↓
Record Fits?
   ↓
Store Record + Slot Entry
```

Free-space management therefore determines whether a page can accommodate a record operation.

---

# 3.8 Record Insert

Record Insert is the process of storing a new record inside a MyRDB page.

Example:

```sql
INSERT INTO Students VALUES (101, 'Aman', 20);
```

MyRDB eventually needs to transform this SQL request into physical record storage.

---

## Basic Insert Flow

```text
INSERT SQL
   ↓
Parser
   ↓
Logical Record
   ↓
Serialize Record
   ↓
Find Page with Free Space
   ↓
Store Record Bytes
   ↓
Create Slot Entry
   ↓
Update Page Metadata
```

---

## Step 1 — Create Record

Logical record:

```text
ID   = 101
Name = Aman
Age  = 20
```

---

## Step 2 — Serialize

```text
Record
   ↓
Bytes
```

---

## Step 3 — Check Free Space

Example:

```text
Free Space = 500 bytes

Record     = 15 bytes
Slot Entry = 8 bytes

Required   = 23 bytes
```

Since the required space is available, the record can fit.

---

## Step 4 — Store Record

The serialized record bytes are written into available page space.

Suppose the record starts at:

```text
Offset = 100
```

---

## Step 5 — Create Slot

The Slot Directory receives:

```text
Slot 0 → Offset 100, Length ...
```

The length depends on the serialized record format.

---

## Step 6 — Update Page Metadata

The page metadata needs to reflect the operation.

Relevant information includes:

* Record count
* Free space
* Slot information

---

## Small Example

```python
record = b"101,Aman,20"

offset = 100
length = len(record)

print(offset)
print(length)
```

The example record occupies 11 bytes.

Therefore conceptually:

```text
Slot 0 → Offset 100, Length 11
```

This is a learning example; the final record format can be more structured.

---

## What If the Page Is Full?

Suppose:

```text
Free Space = 10 bytes
Required Space = 23 bytes
```

The record cannot fit.

The storage engine must then:

```text
Check another page
        ↓
Suitable page?
    ┌───┴───┐
   Yes      No
    ↓        ↓
  Use it   Create Page
```

This connects record insertion with multi-page storage.

---

# 3.9 Record Read

After records are inserted, MyRDB needs to retrieve them.

Record Read is the foundation of future record retrieval operations.

---

## Basic Read Flow

```text
Page
 ↓
Find Slot
 ↓
Get Offset + Length
 ↓
Read Record Bytes
 ↓
Deserialize
 ↓
Return Record
```

---

## How Does MyRDB Locate a Record?

Suppose the Slot Directory contains:

```text
Slot 0 → Offset 100, Length 15
```

MyRDB receives:

```text
Slot ID = 0
```

It looks up Slot 0:

```text
Slot 0
  ↓
Offset = 100
Length = 15
```

Then it reads:

```text
15 bytes starting at byte 100
```

---

## Small Example

```python
page_data = b"...............101,Aman,20"

offset = 15
length = 11

record_bytes = page_data[offset:offset + length]

print(record_bytes)
```

The important operation is:

```python
page_data[offset:offset + length]
```

This means:

```text
Start at Offset
Read Length bytes
```

---

## Deserialization

After reading the bytes:

```text
Record Bytes
     ↓
Deserialization
     ↓
Logical Record
```

Example:

```text
b"101,Aman,20"
       ↓
101, Aman, 20
```

---

## INSERT vs READ

### INSERT

```text
Record
   ↓
Serialize
   ↓
Bytes
   ↓
Page
```

### READ

```text
Page
   ↓
Bytes
   ↓
Deserialize
   ↓
Record
```

Therefore, Record Read is essentially the reverse direction of Record Insert.

---

## Complete Read Flow

```text
Page ID + Slot ID
        ↓
Slot Directory
        ↓
Offset + Length
        ↓
Record Bytes
        ↓
Deserialization
        ↓
Logical Record
```

---

# 3.10 Record Update

Record Update means modifying an existing record already stored in a page.

Example:

```sql
UPDATE Students
SET Age = 21
WHERE ID = 101;
```

Existing record:

```text
101, Aman, 20
```

Updated record:

```text
101, Aman, 21
```

---

## Basic Update Flow

```text
UPDATE SQL
    ↓
Find Record
    ↓
Page ID + Slot ID
    ↓
Get Offset + Length
    ↓
Read Existing Record
    ↓
Modify Record
    ↓
Serialize Again
    ↓
Check Available Space
    ↓
Store Updated Record
    ↓
Update Slot Entry
```

---

## Why Is Update More Complicated Than Read?

Because the size of the record can change.

Example:

```text
Old:
101, Aman, 20
```

could become:

```text
101, Aman Kumar, 20
```

The new record is larger.

Therefore, MyRDB cannot always overwrite the old location blindly.

---

## Case 1 — New Record Fits

Example:

```text
Old Length = 20 bytes
New Length = 18 bytes
```

The new record can potentially use the existing physical location.

```text
Old Record
   ↓
Update
   ↓
New Record
   ↓
Same location
```

---

## Case 2 — New Record Is Larger

Example:

```text
Old Length = 20 bytes
New Length = 35 bytes
```

The old location may not have enough space.

Conceptually:

```text
Old Record
    ↓
New Record Is Larger
    ↓
Find Free Space
    ↓
Store New Record
    ↓
Update Slot Entry
```

The Slot ID can continue to identify the logical storage entry while the slot's offset and length are updated.

---

## Small Example

Suppose:

```text
Slot 0 → Offset 100, Length 15
```

After an update, the new record may have a different length.

The Slot Directory can become:

```text
Slot 0 → Offset 100, New Length
```

or, if the record moved:

```text
Slot 0 → New Offset, New Length
```

---

## Important

An UPDATE does not necessarily mean modifying the exact same physical bytes.

Depending on the record size and available page space:

* The record may be updated in place.
* The record may move to another location.
* The Slot Directory may need to be updated.

---

# 3.11 Record Delete

Record Delete is the process of removing an existing record from a page.

Example:

```sql
DELETE FROM Students
WHERE ID = 101;
```

Suppose:

```text
Slot 0 → Offset 100, Length 20
```

contains:

```text
101, Aman, 20
```

After deletion, MyRDB must make the record no longer active and make its storage available for reuse.

---

## Basic Delete Flow

```text
DELETE SQL
   ↓
Find Record
   ↓
Page ID + Slot ID
   ↓
Find Offset + Length
   ↓
Mark / Remove Record
   ↓
Update Slot
   ↓
Mark Space Reusable
   ↓
Update Page Metadata
```

---

## What Happens to the Slot?

Suppose:

```text
Slot 0 → Record A
Slot 1 → Record B
Slot 2 → Record C
```

Delete Record B.

We generally do not shift Record C into Slot 1.

Instead:

```text
Slot 0 → Record A
Slot 1 → Deleted / Free
Slot 2 → Record C
```

This helps maintain stable internal references.

---

## What Happens to the Record Bytes?

Suppose:

```text
Slot 1 → Offset 120, Length 25
```

The record occupies:

```text
120–144
```

After deletion:

```text
120–144
→ No longer an active record
→ Storage can become reusable
```

The physical bytes do not necessarily need to be immediately erased.

---

## Logical Deletion vs Physical Erasure

These are two different concepts.

### Logical Deletion

The record is no longer considered valid or visible.

### Physical Space Reclamation

The storage occupied by the record becomes available for reuse.

Therefore:

```text
Logical Deletion
        ≠
Immediate Physical Erasure
```

---

## Free Space After Delete

Suppose:

```text
Free Space = 300 bytes
Deleted Record = 25 bytes
```

Conceptually:

```text
300 + 25 = 325 bytes
```

However, actual free-space accounting can be more complicated because of:

* Fragmentation
* Slot directory space
* Existing record layout

Therefore, exact free-space accounting is part of the storage design.

---

## Slot Reuse

After deletion:

```text
Slot 0 → A
Slot 1 → Free
Slot 2 → C
```

A future INSERT can potentially reuse Slot 1:

```text
Slot 0 → A
Slot 1 → D
Slot 2 → C
```

This avoids unnecessary creation of new slot identifiers.

---

## Complete Delete Flow

```text
DELETE SQL
    ↓
Parser
    ↓
Executor
    ↓
Locate Record
    ↓
Page ID + Slot ID
    ↓
Slot Directory
    ↓
Offset + Length
    ↓
Mark Record Deleted
    ↓
Mark Space Reusable
    ↓
Update Slot
    ↓
Update Free Space
    ↓
Update Page Metadata
```

### Key Definition

> Record Delete removes a record logically, makes its storage available for reuse, updates the corresponding slot, and maintains correct page and free-space information.
