2.5 Page Header Binary Layout

Page Header is the metadata stored at the beginning of every database page.

In MyRDB, the Page Header contains:

Field	Size	Purpose
Magic	4 bytes	Identifies a valid MyRDB page
Version	2 bytes	Identifies storage format version
Page ID	4 bytes	Identifies the page
Record Count	2 bytes	Number of records in the page
Free Space	4 bytes	Available free space in the page

Total Header Size = 4 + 2 + 4 + 2 + 4 = 16 bytes

Binary Layout
Byte 0–3     → Magic
Byte 4–5     → Version
Byte 6–9     → Page ID
Byte 10–11   → Record Count
Byte 12–15   → Free Space

Since MyRDB uses a 4096-byte page:

4096 - 16 = 4080 bytes

So, 4080 bytes remain for record data, free space, and slot directory.

2.6 Field Sizes & Struct Format

Python struct is used to convert Python values into a fixed binary format for storage.

Struct Format Codes
Code	Meaning	Size
4s	4-byte bytes field	4 B

I	Unsigned integer	4 B

Therefore, MyRDB's Page Header format is:

4s H I H I

Combined:

"4sHIHI"
Meaning
4s → Magic
H  → Version
I  → Page ID

2.7 — Byte Order / Endianness
New Concept

Endianness means the order in which multiple bytes of a value are stored in memory or in a binary file.

Jab hum struct se Page ID, Version, Free Space jaise numbers ko bytes mein convert karenge, toh decide karna padega ki bytes kis order mein store honge.

There are two common byte orders:

1. Little-Endian

The least significant byte is stored first.

Example:

Number = 0x12345678

Little-Endian:
78 56 34 12
2. Big-Endian

The most significant byte is stored first.

Number = 0x12345678

Big-Endian:
12 34 56 78
Why do we need it in MyRDB?

MyRDB stores pages as binary data.

If we don't explicitly define the byte order, 
the same database file could potentially be interpreted differently on different systems.

So MyRDB should have a fixed binary format.

For our project, we'll use Little-Endian.

CHAPTER-3  Record & Slot Managment

3.1 Record Storage Objective
What is a Record?

A record is a complete set of related data representing one row of a table.

Example:

Students
--------------------------------
ID      Name       Age
101     Aman       20

Here:

101, Aman, 20

is one record.

Why is Record Storage Needed?

In Chapter 2, we learned how MyRDB stores and manages pages. However, a page itself is not a database row.

Chapter 3 introduces the mechanism for storing actual records inside pages.

Record vs Page
Record	Page
Represents a logical row	Represents a physical storage unit
Contains actual field values	Contains records and metadata
Example: 101, Aman, 20	Example: 4096-byte page
Logical concept	Physical storage concept
Record Identification

A record will eventually be identified using:

Page ID + Slot ID

The Slot Directory will map the Slot ID to the physical location of the record.

MyRDB Flow
SQL/Table Fields
      ↓
Logical Record
      ↓
Record Storage
      ↓
Page
Small Example
record = {
    "id": 101,
    "name": "Aman",
    "age": 20
}

print(record)

This represents a logical record. It is not yet physically stored in a page.

3.2 Record Structure
What is Record Structure?

Record Structure defines how the fields of a record are organized and represented.

Example:

Student Record

├── Name
└── Age

Why is Record Structure Needed?

Therefore:

3.3 Record Serialization
What is Serialization?

Serialization is the process of converting a logical record into a byte representation that can be stored on disk.

Logical Record
      ↓
Serialization
      ↓
Bytes
      ↓
Page / Disk
Why is Serialization Needed?

A database file stores binary data (bytes).

A Python dictionary such as:

{
    "id": 101,
    "name": "Aman",
    "age": 20
}

cannot simply be written to the binary page in its Python-object form.

Therefore, MyRDB converts the record into bytes.

Simple Example
record = "101,Aman,20"

data = record.encode("utf-8")

print(data)

Output:

b'101,Aman,20'

The string has been converted into bytes.

Deserialization

The reverse process is called deserialization.

Bytes
  ↓
Deserialization
  ↓
Logical Record

Example:

data = b'101,Aman,20'

record = data.decode("utf-8")

print(record)

Output:

101,Aman,20

3.4 Slot Directory
What is a Slot Directory?

A Slot Directory is a structure inside a page that stores the physical location information of records.

It mainly maintains:

Slot ID → Offset + Length

Example:

Slot 0 → Offset 100, Length 20
Slot 1 → Offset 120, Length 25
Slot 2 → Offset 145, Length 18
Why is Slot Directory Needed?

Records may have different sizes.

For example:

101, Aman, 20
102, Rahul, 21
103, Christopher, 22

The serialized records may occupy different numbers of bytes.

Therefore, MyRDB needs a structure that tells it exactly where every record is located.

Page Layout
┌──────────────────────────────┐
│         PAGE HEADER          │
├──────────────────────────────┤
│                              │
│       RECORD STORAGE         │
│                              │
│        Record 1              │
│        Record 2              │
│        Record 3              │
│                              │
│        FREE SPACE            │
│                              │
├──────────────────────────────┤
│       SLOT DIRECTORY         │
│                              │
│ Slot 0 → Offset + Length     │
│ Slot 1 → Offset + Length     │
│ Slot 2 → Offset + Length     │
└──────────────────────────────┘
Slot Entry

A slot entry contains information such as:

Slot ID
Offset
Length

Example:

Slot ID = 1
Offset  = 120
Length  = 25

This means:

The record identified by Slot 1 starts at byte 120 and occupies 25 bytes.

Offset

Offset = starting byte position of the record inside the page.

Example:

Offset = 100

means the record starts at byte 100.

Length

Length = number of bytes occupied by the record.

Example:

Offset = 100
Length = 20

The record occupies:

Byte 100 → Byte 119

So:

Offset tells WHERE to start, and Length tells HOW MANY bytes to read.

Small Example
slot_directory = [
    {"offset": 100, "length": 20},
    {"offset": 120, "length": 25},
    {"offset": 145, "length": 18}
]

print(slot_directory[1])

Output:

{'offset': 120, 'length': 25}

Here:

Slot ID = 1
Offset  = 120
Length  = 25
Complete Record Location Flow
Page ID
   ↓
Slot ID
   ↓
Offset + Length
   ↓
Record Bytes
   ↓
Deserialization
   ↓
Logical Record
Key Relationship
Page ID → Slot ID → Offset + Length → Record

This relationship will become very important when we implement INSERT, SELECT, UPDATE, and DELETE.

3.5 Slot ID — Summary
What we learned
Slot ID is an internal identifier used to identify a record within a page.
A Slot ID points to a slot entry in the Slot Directory.
A slot entry contains the record's:
Offset → where the record starts
Length → how many bytes the record occupies

Example:
Slot 1 → Offset 120, Length 25

This means Slot 1's record starts at byte 120 and occupies 25 bytes.

Slot ID is different from Primary Key.
Primary Key → identifies the logical database record.
Slot ID → identifies its physical storage entry within a page.
Slot IDs are page-local.
Page 0 + Slot 1 and Page 1 + Slot 1 can refer to different records.

When a record is deleted, its slot can become deleted/available instead of shifting all other slots.

Example:
Before: Slot 0 → A, Slot 1 → B, Slot 2 → C
After deleting B: Slot 0 → A, Slot 1 → Deleted, Slot 2 → C

A deleted slot can potentially be reused by a future INSERT.
Most important flow

Page ID → Slot ID → Slot Entry → Offset + Length → Record Bytes

One-line definition

Slot ID identifies a record's slot within a page, while the slot entry provides the offset and length needed to locate that record's bytes.

--------------------------------------------------------------------------------------------------------------------------------------------------

3.6 Record Offset & Length — Short Notes
Record Offset
Offset = starting byte position of a record inside a page.
It tells where the record starts.
Example: Offset = 100 → record starts at byte 100.
Record Length
Length = total number of bytes occupied by the record.
It tells how many bytes to read.
Example: Length = 20 → read 20 bytes.
Example

Slot 1 → Offset = 100, Length = 20

Means:

Start = 100
Read = 20 bytes
Range = 100–119
Important Difference
Page Offset → where the page starts in the .db file.
Record Offset → where the record starts inside that page.
Main Flow

Page ID → Slot ID → Offset + Length → Record Bytes

Offset tells WHERE to start; Length tells HOW MANY bytes to read.

3.7 Free Space Management — Short Notes
Free Space = unused space available inside a page for storing records.
MyRDB must check free space before inserting or updating a record.
Required space includes:
Record size
Slot entry size
Example

Free Space = 500 bytes
Record = 100 bytes
Slot Entry = 8 bytes

Required = 100 + 8 = 108 bytes

Since 500 ≥ 108, the record can fit.

If space is insufficient

Page 0 → Not enough space → Find/Create another page

Free Space Changes
INSERT → free space decreases
DELETE → free space can increase
UPDATE → free space may increase or decrease depending on the new record size
Main Flow

INSERT → Check Free Space → Record fits? → Store Record + Slot Entry

Free Space Management determines whether a page has enough space to store or modify a record.

Record Insert is the process of storing a new record inside a MyRDB page.
